# CLI·AI 비교를 위한 UI 개편 제안

상태: 설계 제안. API 호출과 AI 비교 화면은 구현하지 않았다. 기존 파스텔 배경·연보라 테마·큰 시계·구름 고양이를 유지한다. 플로팅 창과 패널 이동을 다시 도입하지 않는다.

## 1. 앱의 정보 구조

앱의 기본 목적을 ‘Unity 도구와 모델의 작업 수행을 비교하는 실험실’로 정한다. 왼쪽 탐색은 **실험 만들기 / 실행 기록 / 연결·환경**으로 제한한다. 중앙은 실제 작업 공간, 오른쪽은 큰 시계·현재 단계·완료 수·최근 알림을 보여주는 고정 영역이다. 주요 설정·실행·내보내기 버튼을 오른쪽에 중복 배치하지 않는다.

실험 만들기의 첫 선택은 **CLI 속도 비교 / AI 작업 수행 비교**이다. 이후 중앙 상단에 **준비 / 실행 / 결과**를 유지한다. 실행 중에도 다른 화면을 볼 수 있고, 진행 중 실험으로 돌아가는 위치는 고정한다. 긴 상세 기록은 접어서 두고 화면 안 스크롤 영역을 겹치게 만들지 않는다.

## 2. 비교 축을 구분한다

| 실험 | 바꾸는 대상 | 고정하는 조건 | 대표 결과 |
|---|---|---|---|
| CLI 속도 | UnityBridge·Go CLI·공식 CLI 및 버전 | 작업 코드·Unity·반복 조건 | 완료 시간·성공률·부하 안정성 |
| AI 작업 수행 | API 제공자·모델·모델 설정 | 같은 CLI/Connector·프롬프트·도구 목록·초기 프로젝트 | 성공률·검증 완료까지 시간·비용·도구 호출 수 |
| 조합 비교, 후속 단계 | 모델 × CLI 조합 | 과제·초기 상태·제한·검증 기준 | 어느 조합에서 차이가 났는지 |

AI 비교의 기본 모드에서는 CLI 하나를 고정한다. 모델과 도구를 동시에 바꾸면 모델이 나아서 달라졌는지 CLI가 빨라서 달라졌는지 분리하기 어렵기 때문이다. 조합 비교를 추가할 때는 단일 순위 대신 두 축의 표로 표시한다. 같은 AI 실험 안에서 대상마다 다른 명령 권한이나 숨은 힌트를 주지 않는다.

## 3. 준비 화면

CLI 모드는 현재 실험 선택과 버전 선택을 재사용한다. 자동 발견한 Unity와 릴리스 파일 준비는 접힌 환경 요약으로 표시하고, 문제가 있을 때만 해결 동작을 드러낸다.

AI 모드의 중앙에는 큰 **공통 프롬프트 입력창**을 둔다. 위에는 과제 이름과 저장된 프롬프트 불러오기, 아래에는 다음 세 묶음을 배치한다.

- **비교할 모델**: 연결한 제공자·모델 다중 선택, 실제 모델 식별자, 지원 기능. 준비된 키의 상태만 표시한다.
- **실험 조건**: 고정 CLI/Connector, 초기 프로젝트 템플릿, 반복 횟수. 고급 항목에는 시스템 지시문·도구 스키마·지원되는 생성 옵션을 둔다.
- **성공 조건과 실행 한도**: 검증 항목, 전체 제한 시간, API 턴 수·도구 호출 수·출력 한도, 다음 호출을 허용할 예산 기준.

기본 화면은 미리 만들어진 과제를 선택하면 대부분 채워지도록 한다. 사용자 과제의 성공 조건을 자동 추측해서 확정하지 않는다. 자유 프롬프트만 입력하고 검증 기준이 없으면 ‘탐색 실행’으로 명확히 구분하고 성공률 순위에서 제외한다.

프롬프트·검증 기준·허용 도구는 실험 시작 시 하나의 버전으로 고정한다. 시작 후 편집은 다음 실험 초안에 반영한다. 과거 기록의 ‘이 설정으로 새 실험’은 프롬프트와 실제 모델·도구 버전까지 복원한다.

## 4. 모델이 실제로 작업하는 방식

Desk가 API에 공통 프롬프트와 허용 도구 목록을 전달한다. 모델은 구조화된 도구 호출을 반환한다. Desk는 이름·인수·대상 프로젝트·허용 범위를 검증하고 선택한 CLI를 실행한다. 응답을 모델에 돌려주고 이 과정을 반복한다. 모델이 완료를 선언하거나 한도에 도달하면 독립 검증기가 결과를 검사한다.

모델의 ‘완료했습니다’라는 문장은 성공 판정이 아니다. 모델은 검증기와 정답 정의를 수정할 권한을 갖지 않는다. 구조화된 도구 호출을 지원하는 모델을 우선 연결하고 제공자별 요청·응답 차이는 API 어댑터에서 처리한다. 자연어 응답에서 임의로 명령을 추출하는 방식을 기본으로 삼지 않는다.

과제 예시는 ‘빈 씬에 Plane과 Rigidbody가 있는 Cube를 만들고, 정해진 시간 동안 실행했을 때 Plane 위에 멈추도록 한다’이다. 검증기는 오브젝트·컴포넌트·초기 위치·정해진 물리 조건을 확인한다. 검증 시간과 허용 오차도 과제에 고정한다. Unity 준비를 마친 뒤 모델 실행 시간을 시작한다.

## 5. 실행 화면

상단에 과제명·현재 모델·반복 회차·경과 시간·한도를 표시한다. 중앙에는 ‘모델 응답 대기 → 요청한 Unity 작업 → 실행 결과 → 최종 검증’의 짧은 작업 기록을 보여준다. 원본 API 응답·명령 인수·로그는 상세 보기로 둔다. 모델의 비공개 추론을 보여준다고 표시하지 않는다.

주요 동작은 **중단** 하나이다. 이미 끝난 결과는 즉시 열 수 있고 중단해도 완료 기록과 발생 비용을 남긴다. API 제한·인증 오류·모델의 잘못된 명령·Unity 실행 실패·정답 불일치를 구분한다. 인증·네트워크 장애를 모델 능력 실패로 일괄 계산하지 않는다.

초기에는 로컬 Unity 부하 간섭을 피하도록 실험을 순차 실행한다. 실행 순서는 반복 블록마다 균형 있게 바꾼다. API 서버 혼잡과 비결정성은 로컬 초기화로 제거할 수 없으므로 반복 결과와 호출 시각을 함께 기록한다.

## 6. 결과 화면

AI 결과의 첫 화면은 **모델 / 성공한 시행·평가 대상 / 성공 시 평균 완료 시간 / 총 사용량·추정 비용 / 도구 호출 수** 표와 선택 지표의 세로 그래프로 구성한다. 그래프마다 대상 순서와 색을 유지한다. 성공률과 속도를 하나의 임의 종합 점수로 합치지 않는다.

성공 시 완료 시간은 프롬프트 전송부터 최종 검증 완료까지로 정의하고, API 대기·도구 실행·검증 시간을 상세에서 나눠 보여준다. 전체 벽시계와 세부 구간의 관계를 기록해 병렬 호출 시간을 중복 합산하지 않는다. CLI 자체 벤치의 시간 범위와 AI 전체 완료 시간을 같은 그래프에 섞지 않는다.

실패 시행도 비용·요청 수·오류 기록에 포함한다. 실패 시간을 0ms로 넣거나 빠른 실패를 성능 우위로 표시하지 않는다. 모델별 토큰 집계 방식과 캐시·추론 토큰의 차이를 기록하고 미제공 정보는 ‘미제공’으로 표시한다. 비용은 제공자가 반환한 사용량과 기록된 단가·통화를 기준으로 계산한 추정치이며 실제 청구액과 구분한다.

텍스트 요약은 ‘같은 과제에서 A는 5회 중 4회, B는 5회 중 3회 성공했다. 공동 성공한 시행에서 A의 평균 완료 시간이 ...였다’처럼 성공 표본과 시간 비교 범위를 함께 밝힌다. 시행 상세에는 공통 프롬프트·모델 식별자·설정·도구 스키마·도구 호출 순서·검증 결과를 보관한다.

## 7. 연결·환경과 키 관리

Unity 경로·CLI 릴리스·API 제공자 설정은 준비 화면에서 분리한다. 연결·환경에서 한 번 등록하고 실험에서는 준비된 연결을 선택한다. 키는 Windows 보호 저장소를 이용해 보관하고 로그·결과·GitHub 내보내기에서 제외한다. 입력창에는 저장된 키 원문을 다시 표시하지 않는다.

API 호출은 실험 시작 버튼을 통해 수행하며 선택한 모델 수·과제 수·반복 수·호출 한도와 비용 발생 사실을 시작 전에 보여준다. 비용 상한은 다음 호출 전에 확인할 수 있는 추정치 기반 중단 기준으로 설명한다. 이미 시작된 요청의 비용까지 정확히 차단한다고 보장하지 않는다.

제공자별로 지원하지 않는 생성 옵션을 몰래 생략해서 같은 조건으로 표시하지 않는다. 공통 지원 옵션과 각 모델의 추가 옵션을 구분하고 결과에 기록한다. 여러 제공자의 ‘temperature’나 동일한 seed 숫자가 동등한 생성 조건·재현성을 보장한다고 가정하지 않는다.

## 8. 적용 순서

1. 화면 구조와 두 실험 흐름의 시안을 확정한다.
2. 공통 프롬프트·모델 연결·제한·검증 기준을 저장하는 실험 정의를 만든다.
3. API 어댑터와 도구 호출 실행기를 연결해 하나의 과제를 끝까지 검증한다.
4. 복수 모델의 반복 실행과 결과 비교를 연결한다.
5. 모델 × CLI 조합 비교를 추가한다.

기존 CLI 벤치와 측정 기록은 그대로 읽을 수 있게 유지한다. 현재까지 구현된 Go 비교는 이 설계의 CLI 모드에 배치한다. API 모델 비교와 화면 개편은 별도 합의 후 구현한다.
