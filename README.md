# UnityBridge Desk v0.5.0

**v0.5.0은 v0.4.0 이후의 UI·UX 개편, 아라·아샤 개선, 벤치마크 방법론을 통합한 정식 배포본입니다.** 좌측 탐색과 준비·진행·결과 흐름, 파스텔 풍경·일반 화면, 설정 팝업, 두 캐릭터의 개별 표시·행동을 포함합니다. 평균 차이에 신뢰구간과 측정 근거를 더해 결과를 해석하고 다음 실험을 준비할 수 있습니다. [v0.5.0 릴리스](docs/releases/v0.5.0.md)

**측정 방법론 업데이트:** [Kalibera·Jones(2013)](https://kar.kent.ac.uk/33611/)를 바탕으로 새 프로젝트 시행 단위의 평균 95% 신뢰구간, 블록 쌍의 시간비·감소율 구간, 예비 측정과 다음 실험의 반복 수 제안, 호출·시행 순서 그래프를 추가했습니다. 유효 시행/쌍 5개 미만은 판단을 유보합니다. **준비 → 반복 설계용 예비 설정**, **결과 → 기준 버전 대비 → 측정 신뢰도와 다음 실험**에서 사용합니다. 보고서의 `04_측정근거.txt`에 수식·가정·제안을 함께 저장합니다. [적용한 수식과 범위](docs/STATISTICAL-METHODOLOGY.md)

별도 **[리틀 모델 엔진 v0.1.0](docs/COMPANION.md)**에서 아라와 아샤를 작업표시줄·열린 창 테두리에서도 실행할 수 있습니다. 실행 파일은 `LittleModelEngine.exe`이며 Unity 설치가 필요하지 않습니다. Desk와 캐릭터 파일·동작·설정·실행 상태를 자동으로 동기화하지 않습니다.

<img src="design/branding/desk-icon.png" width="96" alt="구름 고양이 마스코트" />

**UnityBridge 릴리스별 명령 완료 시간과 부하 조건의 안정성을 같은 PC·Unity 조건에서 비교하는 Windows 벤치마크 앱입니다.**

v0.4.0에서 도입한 동일 C#의 **exec 시험(F04)**, UnityBridge 명령의 **고부하·고밀도 시험(S01)**, 시간·유효 완료율 그래프도 포함합니다. S01은 요청 수·동시 요청 수를 제한하며, 기본 5개 시나리오 외에 명령과 입력·기대 결과를 직접 지정할 수 있습니다. 모든 명령의 인수와 선행 상태를 자동 생성하는 기능은 아닙니다. [부하 설계와 범위](docs/STABILITY.md)

앱은 **준비 → 진행 → 결과** 흐름으로 동작합니다. 벤치용 CLI·Connector 준비, 새 프로젝트 생성과 정리는 자동입니다. 좌측은 탐색, 중앙은 설정과 결과에 사용합니다. 파스텔·연보라 색조를 유지하면서 시계와 진행 상태는 상단에 작게 배치했습니다. 고양이 **아라**와 여우 **아샤**는 버튼과 글자 줄을 발판으로 탐색하는 작은 동반자입니다. 한 마리만 표시하거나 둘 다 표시하고, 모두 숨길 수도 있습니다.

**설정** 팝업에서 연보라·로즈·민트 풍경 또는 배경 없는 **일반 화면**을 선택합니다. **캐릭터**에서는 아라와 아샤의 표시·탐색·활동량을 각각 설정하며 다음 실행에도 복원합니다. 아라는 높은 곳을 선호하고 앞발로 장난칩니다. 아샤는 넓고 낮은 발판을 빠르게 돌아다니며 냄새 맡듯 살피고 풍성한 꼬리로 반응합니다. 기존 고양이의 그림과 설정은 아라에 이어집니다. 끌어 놓으면 아래로 떨어져 두 발과 몸이 들어갈 수 있는 실제 발판에 착지하며, 글자·입력칸과 겹친 곳에서도 낙하가 시작됩니다. 벤치·설정 팝업 중에는 둘 다 숨고 정지하며 앱 비활성화·최소화·움직임 끄기에도 멈춥니다. [아라와 아샤 사용법·설계·검증](docs/CHARACTERS.md) · [화면 모션](docs/MOTION.md)

화면 반응은 차분하게 줄였습니다. 결과와 시행 상세는 즉시 바뀌며 본문 이동·버튼 축소 효과를 없앴습니다. 두 캐릭터는 입력·스크롤 중에는 착지를 마친 뒤 쉬고, 포인터를 잠시 올려둘 때만 바라봅니다.

좌측 **벤치 준비 / 실행 기록**은 언제든 사용할 수 있습니다. 실행 기록에서 날짜·버전·상태로 검색한 뒤 선택한 결과를 엽니다. `Ctrl+N`은 준비, `Ctrl+H`는 기록, `Escape`는 실행 기록에서 작업으로 복귀하거나 설정 팝업을 닫습니다. 준비가 부족하면 **확인할 설정으로**를 눌러 해당 입력으로 이동합니다. 사이드바 접기·펼치기 선택도 저장합니다.

결과는 **전체 조건 비교표**에서 먼저 훑고, 행을 선택해 세로 그래프와 시행 상세로 확인합니다. 비교 대상과 기준, 단위, 유효 쌍 수를 함께 표시합니다. 같은 창에서는 조건·기록별 검색·필터·시행 선택·보기와 스크롤을 기억합니다. 준비 화면은 UnityBridge·공식 CLI·Go를 같은 형태의 선택 행으로 표시합니다. [화면 구성과 미리보기](docs/UI-NAVIGATION.md)

준비 화면 하단에서 버전·조건·예정 시행 수를 확인하고 시작합니다. 진행 화면은 실제 단계와 종료한 시행 수를 표시하며, 상세 로그는 펼쳐 봅니다. 종료 후 화면을 강제로 바꾸지 않으며 **결과 확인** 또는 결과 탭으로 이동합니다. 조건별 시간·기준 버전 대비 비교·시행 상세는 그대로 제공하고, 환경·성공·실패 수는 **시험 요약**에서 펼쳐 확인합니다. `Alt+1·2·3`으로 탭을 이동할 수 있습니다.

좌측에는 준비 목차, 진행 시행 목록, 결과의 **실험 → 조건 → 시행 번호**를 배치했습니다. 중앙의 **조건별 시간 / 기준 버전 대비 / 시행 상세**를 전환하고, 시행 번호나 그래프 막대를 선택해 상세를 확인합니다. 번호 검색·상태 필터·실행 기록 검색·설정 재사용·현재 그래프 저장을 지원합니다. 진행 중 다른 시행을 읽어도 선택을 유지하며 **현재 시행으로** 버튼으로 돌아갑니다. 좁은 창에서는 사이드바 아이콘 또는 `Alt+0`으로 좌측을 펼칩니다. [새 화면 안내](docs/UI-NAVIGATION.md)

‘첫 명령 완료 시간’은 사전 실행 0회 뒤 명령 1회, ‘반복 명령 평균 시간’은 W회 사전 실행을 제외한 M회 평균입니다. 두 조건 모두 Unity 준비 후부터 측정하며 서로 다른 새 프로젝트를 씁니다. 횟수와 단위를 화면에 표시합니다. v0.1.3처럼 옵션이 다른 CLI는 Unity 실행 전 도움말로 확인하고 지원 인수만 사용합니다. [CLI 호환성 근거](docs/CLI-COMPATIBILITY.md)

## 다운로드와 실행

1. 전달받거나 GitHub Releases에 첨부된 실행용 **`UnityBridgeDesk-v0.5.0-win-x64.zip`**을 준비합니다.
2. ZIP을 **모두 압축 해제**하고 맨 위의 **`UnityBridge Desk 실행.exe`**를 엽니다. 옆의 `app` 폴더도 필요합니다.
3. 자동으로 찾은 Unity를 확인하고 비교할 릴리스 2~8개를 선택합니다. 공식 Unity와 비교하려면 **공식 Unity CLI + Pipeline 함께 비교**를 켜고 UnityBridge 릴리스를 1~7개 선택합니다.
4. **벤치 시작**을 누릅니다. 파일 준비·임시 프로젝트 생성·측정·결과 저장·정리는 자동입니다.
5. **결과** 탭에서 평균 시간 차이와 세로 그래프를 먼저 확인합니다. **기준 버전 대비**와 **시행 상세**로 근거를 확인하고, **내보내기**에서 TXT·Excel·SVG 또는 결과 폴더를 엽니다. **시험 요약**에는 전체 환경과 판정이 있습니다.

Windows x64와 설치·활성화된 Unity Editor가 필요합니다. Unity가 없다면 Unity Hub에서 먼저 준비하세요. 다른 위치의 Editor는 실행 파일 선택으로 지정할 수 있습니다. 가상머신·ISO·BIOS 변경·별도 Windows 계정은 필요하지 않으며 .NET 런타임은 실행용 ZIP에 포함됩니다.

GitHub의 자동 **Source code ZIP은 실행 파일이 없는 소스**입니다. Desk 앱의 `v0.5.0`과 비교 대상 UnityBridge의 `0.2.0`, `0.2.1`, `0.2.2-rc.2` 등은 서로 다른 버전입니다.

## 무엇을 비교하나요?

**Go unity-cli 함께 비교 · 비공식**을 켜면 [youngwoocho02/unity-cli](https://github.com/youngwoocho02/unity-cli)의 CLI와 같은 태그의 Connector를 비교 대상으로 추가합니다. 기본 선택은 `v0.4.1`이며 Unity 6가 필요합니다. Go 대상과 UnityBridge 또는 공식 Unity를 합쳐 2~8개를 선택하고 기존 **벤치 시작** 버튼을 사용합니다. 별도 Go 설치나 터미널 입력은 필요하지 않습니다. [Go 비교 조건·임시 설치·정리](docs/GO-UNITY-COMPARISON.md)

**준비 → 비교 대상 → 공식 Unity CLI + Pipeline 함께 비교**를 켜고 **벤치 시작**을 누르면 공식 도구도 자동 준비해 비교합니다. 설치·활성화된 Unity 6가 필요합니다. 버전 입력은 선택 사항이며, 실제 사용 버전과 의존 패키지 해시를 기록합니다. 같은 작업·측정 루프로 F01~F04와 공통 S01 시나리오를 실행하고 기존 결과 화면에서 확인합니다. [사용법과 공정한 비교 범위](docs/OFFICIAL-UNITY-COMPARISON.md)

공식 CLI·Pipeline은 앱 전용 `speed/official-work` 아래에 임시로 내려받고 벤치 종료·오류·취소 시 삭제합니다. 시행별 실행 복사본과 공식 CLI의 설정·캐시용 경로도 분리하며 삭제 여부를 결과에 기록합니다. 다음 벤치에는 원본을 다시 내려받고, 준비·삭제 시간은 속도 통계에 넣지 않습니다. Windows 공용 캐시와 Unity 라이선스 서비스까지 초기화하는 방식은 아닙니다.

비교 대상은 **공식 배포 CLI + 같은 태그의 Connector 조합**입니다. 모든 버전에 같은 벤치 도구 `desk_probe`를 넣고 앱이 고정 명령을 직접 보냅니다. 요청 식별자·프로젝트 경로·포트는 시행마다 달라지지만 작업 내용·개수·응답 조건은 같습니다. AI 호출, 프롬프트 해석, 토큰 생성 시간은 측정하지 않습니다.

F01에서 사용하는 도구 호출의 예시입니다.

```text
call desk_probe --params '{"action":"echo","nonce":"요청 식별값"}'
```

UnityBridge 호출에는 JSON 응답, 프로젝트·포트 지정, 업데이트 확인 비활성화 등의 옵션이 붙으며 전체 인수는 결과에 저장됩니다. Go CLI는 `call` 접두어 없이 `desk_probe --params ...`를 사용하고, 프로젝트·밀리초 단위 제한 시간을 지정합니다. 각 CLI의 실제 문법과 응답 형식은 다르지만 Unity에서 수행하는 작업과 검증 기준은 같습니다.

| 실험 | 동일하게 수행하는 작업 | 비교하는 지점 | 해석할 때의 범위 |
|---|---|---|---|
| F01 first / prepared | 값 `42`를 반환하는 작은 echo. 첫 명령은 1회, 반복 평균은 W회 사전 실행 뒤 M회 측정 | 작은 요청의 기본 왕복 비용과 첫 사용 시 추가 비용 | 첫 명령은 **새 Unity가 컴파일·Bridge ready를 마친 뒤 처음 보내는 명령**. Unity 시작 시간이나 차가운 OS 캐시의 성능이 아님 |
| F02 1 / 10 / 100 | 동일한 오브젝트 1,000개 이동을 각각 1·10·100개 명령으로 나눔 | 작업량이 같을 때 호출을 잘게 나누면서 늘어나는 전체 완료 시간 | 명령마다 새 CLI가 시작됨. Unity 연산만의 속도나 순수한 네트워크 지연으로 해석하지 않음 |
| F03 1 KiB / 64 KiB / 1 MiB | 정해진 ASCII 반복 본문을 반환 | 응답이 커지면서 늘어나는 생성·직렬화·전달·출력 수집 비용 | 크기는 본문 기준. JSON 포장과 식별 정보가 붙은 전체 응답은 더 큼 |
| F04 first / prepared | 같은 C# 파일을 exec로 실행해 값·대상 반환 | CLI·전달·C# 컴파일·실행의 완료 시간 | 반복 조건에서도 각 exec 요청의 컴파일이 포함됨 |
| S01 명령 부하 | 시나리오별 요청 수·동시 요청 수·입력 고정 | 요청 밀집 시 시간, 오류, 완료율과 처리량 | 기본 32개·동시 4개. Unity 내부 병렬 실행이나 모든 명령의 자동 검증을 뜻하지 않음 |

F01~F03은 **첫 사용 비용, 호출 분할 비용, 응답 크기 비용을 나누어 관찰하려는 설계**입니다. F04는 컴파일·실행 경로를, S01은 요청 밀도가 높을 때의 지연·오류·처리량을 별도 조건으로 관찰합니다. 단순한 작업을 고정해 차이가 나타난 조건을 설명하기 쉽게 합니다. 모든 Unity 도구나 실제 게임 제작 작업의 성능을 대표하는 표준 시험은 아닙니다.

## 벤치 설계의 근거

### 1. 시간의 시작과 끝을 고정합니다

고해상도 `Stopwatch`로 **CLI 프로세스 시작 직전부터 종료와 stdout/stderr 수집 완료까지** 측정합니다. Windows의 `Stopwatch`는 경과 시간 측정에 적합한 성능 카운터를 사용합니다. 시간 구간을 명시하는 이유는 버전별로 같은 완료 조건을 비교하기 위해서입니다. [Microsoft 고해상도 시간 측정](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)

| 측정에 포함 | 측정에서 제외 |
|---|---|
| CLI 시작·초기화, 명령 처리, Connector 통신, 출력 읽기·디코딩, 프로세스 종료 | 다운로드·RC ZIP 압축 해제·파일 복사·해시 검사, Worker 시작, Unity 기동·컴파일·ready 대기, 준비 호출, 측정 후 응답 검증·정리 |

F04의 **exec 요청이 수행하는 C# 컴파일은 포함**됩니다. S01 개별 시간도 같은 경계이며, 부하 처리량용 전체 구간은 요청 준비·응답 검증·공급 간격을 포함합니다. 성공률·시간 변동·호출 P95의 분모와 한계는 [안정성 설계](docs/STABILITY.md)에 명시합니다.

F02의 전체 시간은 첫 명령 시작부터 마지막 응답 수집까지이므로 **명령 사이의 앱 실행 제어 간격도 포함**합니다. 구버전 EXE가 실행 중 자체 런타임을 추출하는 비용은 포함하고, RC ZIP을 미리 푸는 설치 비용은 제외합니다. 따라서 결과 차이는 공식 배포 조합의 완료 시간 차이이며 Connector 내부 코드 하나의 개선 효과로 단정할 수 없습니다.

### 2. 같은 조건의 버전을 가까이 배치합니다

같은 조건·반복 차수의 버전들을 한 블록으로 묶고, 반복마다 시작 버전을 회전합니다. 시드는 이 회전 순서를 재현하는 데 사용합니다. 시간대·온도 등 관심 대상 밖의 요인이 비교에 섞이는 것을 줄이려는 설계입니다. 이는 NIST의 블록화·무작위화 원칙을 참고한 것으로, 현재 구현 자체가 완전 무작위 블록 실험이라는 뜻은 아닙니다. [NIST 블록 실험 설계](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)

반복 수가 버전 수의 배수일 때 각 실행 위치의 횟수가 맞습니다. 그 외에는 완전히 균형 잡힌 순서가 아니며 실험 조건의 순서도 고정입니다. 외부 부하·발열·전원 상태를 자동으로 고정하거나 보정하지 않습니다.

### 3. 앞선 시행의 파일과 실행 상태를 줄입니다

매 시행 새 프로젝트·Library·CLI 복사본·TEMP/TMP·UPM 캐시를 만들고 Unity·CLI를 새 프로세스로 실행합니다. 이전 시행이 만든 오브젝트·프로젝트 파일·프로세스 메모리를 직접 재사용하지 않기 위한 조치입니다. 패키지 캐시는 Unity가 제공하는 환경 변수로 시행별 경로를 지정합니다. [Unity 패키지 캐시 설정](https://docs.unity3d.com/6000.0/Documentation/Manual/upm-config-cache.html)

시험 프로세스는 Windows Job Object로 묶어 중단·종료 시 수명을 관리하고, 소유권과 종료를 확인한 뒤 시험 폴더만 정리합니다. Job Object는 프로세스 관리 기능이며 그 자체로 사용자 설정이나 파일 접근까지 격리하는 OS 샌드박스는 아닙니다. [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

**Windows 계정·사용자 설정·라이선스 서비스·네트워크·시스템 캐시는 공유합니다.** Windows는 파일 데이터를 메모리에 캐시하므로 새 프로젝트와 새 프로세스만으로 OS 캐시가 초기화되지 않습니다. 준비 중의 복사·해시 검사도 캐시에 영향을 줍니다. [Microsoft 파일 캐시](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching)

### 4. 빨리 끝났어도 작업이 틀리면 성공으로 세지 않습니다

응답의 값·nonce·Unity PID·프로젝트 경로를 검증합니다. F02는 최종 오브젝트 수·ID·위치를, F03은 본문 전체와 길이를 확인합니다. 다른 프로젝트의 응답, 잘못된 값, 시간 초과, 중단, 정리 실패를 빠른 성공으로 집계하지 않습니다. CLI·Connector·실험 도구의 해시도 기록해 비교한 파일을 식별합니다.

### 5. 호출 수와 독립 반복 수를 구분합니다

한 Unity에서 여러 번 호출한 결과는 그 시행의 평균으로 요약합니다. 이를 여러 개의 독립된 새 프로젝트 시험처럼 세지 않습니다. F02는 시행 전체 시간이 대표값입니다. 새 프로세스의 시행도 같은 Windows 캐시와 부하를 공유하므로 통계적 독립성을 보장하지 않습니다.

버전 비교는 **같은 블록에서 두 버전 모두 성공하고 정리가 확인된 쌍**만 사용합니다. 시간 감소율은 `100 × (1 − 후보 평균 / 기준 평균)`이며 양수이면 후보가 더 짧은 시간에 완료한 것입니다. 이는 성공 쌍에 한정된 기술 통계이므로 실패율과 미수행 수를 함께 봐야 합니다. 실패를 0ms로 넣거나 작은 표본으로 전체 승자를 판정하지 않습니다.

위 공식 문서는 시간 측정·실행 환경·실험 설계 원칙의 근거입니다. 실험별 작업 크기·부하 설정과 현재 분석 방법은 이 앱의 선택이며, 해당 기관이 이 벤치를 인증하거나 특정 버전의 우수성을 보증하는 것은 아닙니다.

## 결과 읽기와 확인한 범위

기본 F01 설정은 새 프로젝트 반복 N=2, 준비 호출 W=1, 준비 후 측정 M=3입니다. 두 버전이면 **8개 시행**이며 동작 확인용입니다. `v0.5.0`은 앱 배포 버전이고 측정 스키마는 `local-cli-completion-v1-pilot`입니다. 분석 규칙 `kj2013-paired-fieller-v1`은 유효 시행/쌍 5개 이상에서 개별 95% 구간을 제공하며, 유의성 검정·전체 승자 판정은 제공하지 않습니다. 5회가 충분한 정밀도를 보장하지는 않습니다.

v0.5.0의 빌드·회귀·배포 검증은 [v0.5.0 검증 기록](docs/V050-VALIDATION.md), 이전 실제 연동은 [v0.4.0 검증 기록](docs/V040-VALIDATION.md)에 구분합니다. 아래 실제 Unity **6000.3.23f1** 연동 결과는 v0.3.0에서 수행한 과거 기록입니다.

| 실제 확인 | 대상 | 결과 |
|---|---|---|
| F01 first / prepared | 0.2.0·0.2.1·0.2.2-rc.2 | 6개 시행 성공·정리 확인 |
| F02 1 / 10 / 100 | 0.2.1·0.2.2-rc.2 | 6개 시행 성공·정리 확인 |
| F03 1 KiB / 64 KiB / 1 MiB | 0.2.1·0.2.2-rc.2 | 6개 시행 성공·정리 확인 |
| Unity 실행 단계에서 중단 | 0.2.1 | 중단 기록·프로세스 종료·정리 확인 |

이 18개 성공은 기능 확인이며 통계적 속도 우열을 입증한 결과가 아닙니다. 확인한 PC·실패한 사전 진단·남은 범위는 [검증 문서](docs/LOCAL-BENCH.md)에 기록합니다. JSON·CSV에는 시행별 원시 값과 실패·미수행이 남으며, 경로와 컴퓨터 이름은 공개 전에 확인해야 합니다.
