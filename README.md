# UnityBridge Desk v0.3.0

<img src="design/branding/desk-icon.png" width="96" alt="구름 고양이 마스코트" />

**UnityBridge 릴리스별 고정 명령의 완료 시간을 같은 PC·Unity 조건에서 비교하는 Windows 속도 벤치마크 앱입니다.**

v0.3.0은 기능 범위를 **속도 벤치**로 축소한 정식 배포입니다. 일반 설치·관리, AI 작업, VM 관리 화면을 기본 앱에서 제외하고 **준비 → 진행 → 결과** 흐름에 집중했습니다. 벤치에 필요한 CLI·Connector 준비는 자동으로 수행합니다. 기존 파스텔 테마와 큰 시계는 유지합니다.

## 다운로드와 실행

1. GitHub **Releases → v0.3.0 → Assets**에서 **`UnityBridgeDesk-v0.3.0-win-x64.zip`**을 받습니다.
2. ZIP을 **모두 압축 해제**하고 맨 위의 **`UnityBridge Desk 실행.exe`**를 엽니다. 옆의 `app` 폴더도 필요합니다.
3. 자동으로 찾은 Unity를 확인하고 비교할 릴리스 2~8개를 선택합니다.
4. **벤치 시작**을 누릅니다. 파일 준비·임시 프로젝트 생성·측정·결과 저장·정리는 자동입니다.
5. **결과** 탭에서 성공·실패·미수행 수를 먼저 확인하고 같은 조건의 시간과 정리 상태를 비교합니다.

Windows x64와 설치·활성화된 Unity Editor가 필요합니다. Unity가 없다면 Unity Hub에서 먼저 준비하세요. 다른 위치의 Editor는 실행 파일 선택으로 지정할 수 있습니다. 가상머신·ISO·BIOS 변경·별도 Windows 계정은 필요하지 않으며 .NET 런타임은 실행용 ZIP에 포함됩니다.

GitHub의 자동 **Source code ZIP은 실행 파일이 없는 소스**입니다. Desk 앱의 `v0.3.0`과 비교 대상 UnityBridge의 `0.2.0`, `0.2.1`, `0.2.2-rc.2` 등은 서로 다른 버전입니다.

## 무엇을 비교하나요?

비교 대상은 **공식 배포 CLI + 같은 태그의 Connector 조합**입니다. 모든 버전에 같은 벤치 도구 `desk_probe`를 넣고 앱이 고정 명령을 직접 보냅니다. 요청 식별자·프로젝트 경로·포트는 시행마다 달라지지만 작업 내용·개수·응답 조건은 같습니다. AI 호출, 프롬프트 해석, 토큰 생성 시간은 측정하지 않습니다.

F01에서 사용하는 도구 호출의 예시입니다.

```text
call desk_probe --params '{"action":"echo","nonce":"요청 식별값"}'
```

실제 호출에는 JSON 응답, 프로젝트·포트 지정, 업데이트 확인 비활성화 등의 공통 옵션이 붙으며 전체 인수는 결과에 저장됩니다.

| 실험 | 동일하게 수행하는 작업 | 비교하는 지점 | 해석할 때의 범위 |
|---|---|---|---|
| F01 first / prepared | 값 `42`를 반환하는 작은 echo. 첫 호출은 1회, 준비 후는 W회 준비 호출 뒤 M회 측정 | 작은 요청의 기본 왕복 비용과 첫 사용 시 추가 비용 | 첫 호출은 **새 Unity가 컴파일·Bridge ready를 마친 뒤 처음 보내는 명령**. Unity 시작 시간이나 차가운 OS 캐시의 성능이 아님 |
| F02 1 / 10 / 100 | 동일한 오브젝트 1,000개 이동을 각각 1·10·100개 명령으로 나눔 | 작업량이 같을 때 호출을 잘게 나누면서 늘어나는 전체 완료 시간 | 명령마다 새 CLI가 시작됨. Unity 연산만의 속도나 순수한 네트워크 지연으로 해석하지 않음 |
| F03 1 KiB / 64 KiB / 1 MiB | 정해진 ASCII 반복 본문을 반환 | 응답이 커지면서 늘어나는 생성·직렬화·전달·출력 수집 비용 | 크기는 본문 기준. JSON 포장과 식별 정보가 붙은 전체 응답은 더 큼 |

이 세 실험은 **첫 사용 비용, 호출 분할 비용, 응답 크기 비용을 나누어 관찰하려는 이 프로젝트의 설계 선택**입니다. 단순한 작업을 고정해 차이가 나타난 조건을 설명하기 쉽게 합니다. 모든 Unity 도구나 실제 게임 제작 작업의 성능을 대표하는 표준 시험은 아닙니다.

## 벤치 설계의 근거

### 1. 시간의 시작과 끝을 고정합니다

고해상도 `Stopwatch`로 **CLI 프로세스 시작 직전부터 종료와 stdout/stderr 수집 완료까지** 측정합니다. Windows의 `Stopwatch`는 경과 시간 측정에 적합한 성능 카운터를 사용합니다. 시간 구간을 명시하는 이유는 버전별로 같은 완료 조건을 비교하기 위해서입니다. [Microsoft 고해상도 시간 측정](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)

| 측정에 포함 | 측정에서 제외 |
|---|---|
| CLI 시작·초기화, 명령 처리, Connector 통신, 출력 읽기·디코딩, 프로세스 종료 | 다운로드·RC ZIP 압축 해제·파일 복사·해시 검사, Worker 시작, Unity 기동·컴파일·ready 대기, 준비 호출, 측정 후 응답 검증·정리 |

F02의 전체 시간은 첫 명령 시작부터 마지막 응답 수집까지이므로 **명령 사이의 앱 실행 제어 간격도 포함**합니다. 구버전 EXE가 실행 중 자체 런타임을 추출하는 비용은 포함하고, RC ZIP을 미리 푸는 설치 비용은 제외합니다. 따라서 결과 차이는 공식 배포 조합의 완료 시간 차이이며 Connector 내부 코드 하나의 개선 효과로 단정할 수 없습니다.

### 2. 같은 조건의 버전을 가까이 배치합니다

같은 조건·반복 차수의 버전들을 한 블록으로 묶고, 반복마다 시작 버전을 회전합니다. 시드는 이 회전 순서를 재현하는 데 사용합니다. 시간대·온도 등 관심 대상 밖의 요인이 비교에 섞이는 것을 줄이려는 설계입니다. 이는 NIST의 블록화·무작위화 원칙을 참고한 것으로, 현재 구현 자체가 완전 무작위 블록 실험이라는 뜻은 아닙니다. [NIST 블록 실험 설계](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)

반복 수가 버전 수의 배수일 때 각 실행 위치의 횟수가 맞습니다. 그 외에는 완전히 균형 잡힌 순서가 아니며 F01·F02·F03 조건의 순서도 고정입니다. 외부 부하·발열·전원 상태를 자동으로 고정하거나 보정하지 않습니다.

### 3. 앞선 시행의 파일과 실행 상태를 줄입니다

매 시행 새 프로젝트·Library·CLI 복사본·TEMP/TMP·UPM 캐시를 만들고 Unity·CLI를 새 프로세스로 실행합니다. 이전 시행이 만든 오브젝트·프로젝트 파일·프로세스 메모리를 직접 재사용하지 않기 위한 조치입니다. 패키지 캐시는 Unity가 제공하는 환경 변수로 시행별 경로를 지정합니다. [Unity 패키지 캐시 설정](https://docs.unity3d.com/6000.0/Documentation/Manual/upm-config-cache.html)

시험 프로세스는 Windows Job Object로 묶어 중단·종료 시 수명을 관리하고, 소유권과 종료를 확인한 뒤 시험 폴더만 정리합니다. Job Object는 프로세스 관리 기능이며 그 자체로 사용자 설정이나 파일 접근까지 격리하는 OS 샌드박스는 아닙니다. [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

**Windows 계정·사용자 설정·라이선스 서비스·네트워크·시스템 캐시는 공유합니다.** Windows는 파일 데이터를 메모리에 캐시하므로 새 프로젝트와 새 프로세스만으로 OS 캐시가 초기화되지 않습니다. 준비 중의 복사·해시 검사도 캐시에 영향을 줍니다. [Microsoft 파일 캐시](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching)

### 4. 빨리 끝났어도 작업이 틀리면 성공으로 세지 않습니다

응답의 값·nonce·Unity PID·프로젝트 경로를 검증합니다. F02는 최종 오브젝트 수·ID·위치를, F03은 본문 전체와 길이를 확인합니다. 다른 프로젝트의 응답, 잘못된 값, 시간 초과, 중단, 정리 실패를 빠른 성공으로 집계하지 않습니다. CLI·Connector·실험 도구의 해시도 기록해 비교한 파일을 식별합니다.

### 5. 호출 수와 독립 반복 수를 구분합니다

한 Unity에서 여러 번 호출한 결과는 그 시행의 평균으로 요약합니다. 이를 여러 개의 독립된 새 프로젝트 시험처럼 세지 않습니다. F02는 시행 전체 시간이 대표값입니다. 새 프로세스의 시행도 같은 Windows 캐시와 부하를 공유하므로 통계적 독립성을 보장하지 않습니다.

버전 비교는 **같은 블록에서 두 버전 모두 성공하고 정리가 확인된 쌍**만 사용합니다. 시간 감소율은 `100 × (1 − 후보 평균 / 기준 평균)`이며 양수이면 후보가 더 짧은 시간에 완료한 것입니다. 이는 성공 쌍에 한정된 기술 통계이므로 실패율과 미수행 수를 함께 봐야 합니다. 실패를 0ms로 넣거나 작은 표본으로 전체 승자를 판정하지 않습니다.

위 공식 문서는 시간 측정·실행 환경·실험 설계 원칙의 근거입니다. F01·F02·F03의 작업 크기와 현재 분석 방법은 이 앱의 선택이며, 해당 기관이 이 벤치를 인증하거나 특정 버전의 우수성을 보증하는 것은 아닙니다.

## 결과 읽기와 확인한 범위

기본 F01 설정은 새 프로젝트 반복 N=2, 준비 호출 W=1, 준비 후 측정 M=3입니다. 두 버전이면 **8개 시행**이며, 이는 동작과 경향을 확인하는 예비 설정입니다. `v0.3.0`은 앱 배포 버전이고 측정 스키마는 `local-cli-completion-v1-pilot`입니다. 신뢰구간·유의성 검정·전체 승자 판정은 제공하지 않습니다.

자동 검사 **170개 통과**와 별도의 실제 Unity **6000.3.23f1** 연동을 확인했습니다.

| 실제 확인 | 대상 | 결과 |
|---|---|---|
| F01 first / prepared | 0.2.0·0.2.1·0.2.2-rc.2 | 6개 시행 성공·정리 확인 |
| F02 1 / 10 / 100 | 0.2.1·0.2.2-rc.2 | 6개 시행 성공·정리 확인 |
| F03 1 KiB / 64 KiB / 1 MiB | 0.2.1·0.2.2-rc.2 | 6개 시행 성공·정리 확인 |
| Unity 실행 단계에서 중단 | 0.2.1 | 중단 기록·프로세스 종료·정리 확인 |

이 18개 성공은 기능 확인이며 통계적 속도 우열을 입증한 결과가 아닙니다. 확인한 PC·실패한 사전 진단·남은 범위는 [검증 문서](docs/LOCAL-BENCH.md)에 기록합니다. JSON·CSV에는 시행별 원시 값과 실패·미수행이 남으며, 경로와 컴퓨터 이름은 공개 전에 확인해야 합니다.

## 저장 위치와 이전 버전

기본 데이터는 `%LOCALAPPDATA%/UnityBridgeDesk/speed` 아래에 보관합니다.

| 위치 | 내용 |
|---|---|
| `local-settings.json` | Unity·버전 선택, 실험 조건, 테마 |
| `releases` | 해시를 확인한 CLI·Connector·RC 런타임 |
| `local-work/<시행 ID>` | 새 임시 작업 공간. 결과 저장 후 삭제 |
| `local-runs/<실행 ID>` | JSON·CSV·요청 명세·로그 |

이전 설정에서 실험 조건·테마·버전 선택을 가져오며 Unity 경로는 새로 탐색합니다. 이전 VM·기록은 보존하고 새 로컬 결과와 합산하지 않습니다. 일반 설치·관리·AI·VM의 일부 기존 코드는 호환성과 회귀 검사를 위해 소스에 남아 있으나 기본 앱의 기능으로 제공하지 않습니다.

## 소스에서 실행과 공개 파일

Windows x64, PowerShell 7, .NET SDK **10.0.400**을 사용합니다.

```powershell
pwsh -File ./build/Verify.ps1 -Restore
pwsh -File ./build/StartDesk.ps1
```

빌드·패키징은 [개발 가이드](docs/DEVELOPMENT.md), GitHub에 올릴 파일과 릴리스 본문은 [업로드 가이드](docs/PUBLISHING.md)를 참고하세요. 실행기 제작에는 MinGW-w64가 필요합니다. 소스 내보내기는 `.gitignore`·MIT 라이선스·검사 워크플로를 포함하며 개인 설정·인증 정보·실제 결과·VM 이미지·다운로드한 외부 바이너리를 제외합니다.
