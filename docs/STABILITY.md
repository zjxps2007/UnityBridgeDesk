# v0.4.0 · exec와 고부하·고밀도 명령 시험

안정성 시험의 대상은 UnityBridge를 통해 전달되는 명령이다. 실행 시간을 길게 늘리는 시험 대신, **한 요청의 작업량과 동시에 진행하는 CLI 요청 수를 정해 짧은 구간에 집중**한다. 모든 명령이 동일한 입력을 받는 것은 아니므로 명령별 시나리오를 만든다. 버전 간에는 같은 시나리오를 전달한다.

## F04: 같은 C#을 exec로 실행한다

앱은 모든 시행에 같은 UTF-8 C# 파일을 생성하고 `exec --file <exec-script.cs>`를 실행한다. 코드는 값 42, 요청 식별자, Unity 프로세스 ID와 프로젝트 경로를 반환한다. 식별자는 별도 입력 파일에서 읽으며, 앱이 그 파일을 쓰는 시간은 측정 밖이다. 코드 파일의 SHA-256을 결과에 기록하고 코드와 마지막 입력 파일을 시행 로그에 보관한다.

- **first**: 새 프로젝트의 Unity·컴파일·Bridge ready 이후 준비 호출 없이 exec를 1회 실행한다.
- **prepared**: 별도의 새 프로젝트에서 같은 exec를 W회 준비 호출한 뒤 M회 측정한다.

CLI 프로세스 시작부터 출력 수집·종료까지 잰다. 파일 읽기, Bridge 전달, C# 컴파일러 실행, 어셈블리 로딩과 코드 실행이 포함된다. Unity의 최초 프로젝트 컴파일은 준비 시간이고, **exec가 요청을 처리하기 위해 하는 C# 컴파일은 측정 시간**이다. 확인한 UnityBridge 0.2.0·0.2.3 구현은 exec 요청마다 컴파일하므로 prepared를 ‘컴파일 생략’이라고 부르지 않는다. [공식 exec 명령 문서](https://github.com/zjxps2007/UnityBridge/blob/main/docs/COMMANDS.md#c-execution)

고정 코드로 기본 exec 경로의 비용을 비교한다. 복잡한 사용자 코드 전체의 성능을 대표하지 않는다. 다른 C# 작업은 아래 S01에 별도 시나리오로 지정할 수 있다.

## S01: 제한된 수의 요청을 계속 채운다

기본값은 **시나리오별 총 32개 요청, 동시 요청 최대 4개**다. 범위는 요청 1~1,000개, 동시 요청 1~16개이며 동시 요청 수는 총 요청 수를 넘을 수 없다. 모든 시나리오를 기본으로 선택하면 5개 조건을 각각 새 프로젝트에서 시험한다. N과 버전 수를 곱하면 전체 시행 수가 된다.

작업자 C개가 요청을 하나씩 보낸다. 응답을 수집하고 검증하면 다음 요청을 보낸다. 설정한 요청 수에 도달하면 종료한다. 고정 초당 요청률을 강제하는 방식이 아니라 **동시 진행 수를 제한한 폐쇄형 부하 방식**이다. 별도 대기 시간을 넣지 않지만 CLI 시작·호출 준비·검증 비용은 요청 공급 속도에 영향을 준다. W·M은 S01에 적용하지 않으며 준비 호출 없이 부하 구간을 시작한다.

UnityBridge의 확인한 CommandRouter 구현은 명령 처리를 직렬화한다. 따라서 ‘동시 요청 4개’는 클라이언트가 최대 4개를 진행한다는 뜻이다. Unity가 네 명령을 병렬로 수행한다는 뜻은 아니다. 기다리는 시간도 각 CLI 완료 시간에 포함된다. 동시에 보낸 요청의 서버 도착 순서는 고정하지 않는다.

| 기본 시나리오 | 전달 명령 | 부하와 검증 |
|---|---|---|
| echo | `desk_probe` / echo | 작은 요청 밀집. 값 42와 식별자·프로젝트·PID 확인 |
| payload | `desk_probe` / payload | 요청당 1 MiB ASCII 응답. 전체 본문과 대상 확인 |
| objects | `desk_probe` / stress_objects | 요청당 GameObject 1,000개 생성 후 finally에서 제거. 반환 개수와 대상 확인 |
| exec | `exec` / code=`return 42;` | 컴파일·실행 요청 밀집. 반환값 42 확인 |
| state | `get_editor_state` | 상태 조회 요청 밀집. 성공 응답 확인 |

오브젝트 시나리오는 객체 생성·제거 경로의 부하를 준다. 물리 시뮬레이션·렌더링 FPS 시험은 아니다. 모든 시나리오는 끝에서 해당 Unity의 기대 상태와 컴파일 오류 여부를 다시 확인한다.

## 다른 UnityBridge 명령을 추가한다

준비 → 실험 조건 조정 → **S01** → **부하 설정 → 다른 UnityBridge 명령 지정**에서 JSON 목록을 넣는다. 빈칸이면 기본 5개 시나리오를 사용한다. 입력한 목록은 기본 목록에 추가되는 것이 아니라 전체 목록을 대체한다. 최대 32개이며 ID는 중복할 수 없다.

예: exec에 실제 계산 작업을 전달한다. 같은 항목을 모든 비교 버전에 사용한다.

```json
[
  {
    "Id": "exec_sum",
    "Command": "exec",
    "ParametersJson": "{\"code\":\"int sum = 0; for (int i = 1; i <= 1000; i++) sum += i; return sum;\"}",
    "ExpectedDataJson": "500500",
    "Description": "1부터 1000까지 합산",
    "ExpectedEditorState": "ready"
  }
]
```

`Command`와 `ParametersJson`은 `call <Command> --params <ParametersJson>`으로 전달한다. CLI 프로젝트·포트는 시험 중인 Unity로 고정한다. 일반 명령의 입력은 그대로 사용하고 `desk_probe`만 매 호출 nonce를 넣는다. `ExpectedDataJson`은 응답의 `data`와 비교한다. 객체는 지정한 필드가 일치하면 되고, 배열과 스칼라는 전체 값이 같아야 한다. 기대 결과를 생략하면 성공 응답 형식·종료 코드와 마지막 Editor 상태를 확인하며, 작업 내용의 의미적 정확성까지 입증하지 않는다.

이 기능은 UnityBridge가 노출한 명령에 입력을 전달하는 공통 실행기다. **모든 내장 명령을 자동으로 열거하고 유효한 인수·선행 상태·성공 조건까지 자동 생성하는 기능은 아니다.** 선택 버전에 없는 명령은 미지원 실패로 기록한다. GUI·화면 캡처, Play Mode, 테스트 구성, 에셋 등 사전 상태가 필요한 명령은 현재의 새 최소 프로젝트·batchmode·nographics 조건에서 실패할 수 있다. 상태를 바꾸는 명령은 `ExpectedEditorState`를 ready/playing/paused 중 맞게 지정한다. 복합 준비 단계와 여러 명령을 섞는 순서 시나리오는 현재 제공하지 않는다.

## 실패를 어떻게 다루는가

호출별 시간·출력 크기·시작 오프셋·성공/실패·오류 종류를 저장한다. 시간 초과, 응답 불일치, 명령 미지원·벤치 호환성 오류 또는 취소가 확인되면 새 요청을 더 보내지 않는다. 이미 보낸 요청은 각 제한 시간 안에서 회수한다. 다른 명령 오류는 설정한 요청 수까지 이어가며 오류가 반복되는지도 기록한다. 자동 재시도로 실패를 가리지 않는다.

오류 종류는 실제 반환된 응답을 근거로 한다. 명령 응답의 `success/data`와 CLI 오류의 `ok:false/error` 형식을 구분하며, CLI가 표준 오류(stderr)에 반환한 연결 검색 실패를 빈 표준 출력의 JSON 오류로 덮어쓰지 않는다. 표준 오류를 성공 응답으로 인정하지 않는다. JSON 자체가 없으면 컴파일 오류로 추정하지 않고 CLI 종료 오류와 stderr를 기록한다. 두 버전에서 확인한 사례는 [검증 기록](V040-VALIDATION.md)에 남긴다.

시행 상세에는 실제 호출 수·응답 검증 통과 수·실패 수·첫 실패 순서를 표시한다. 이전 기록에 `no active instance on port ...`라는 구조화된 오류가 그대로 남아 있으면 화면과 새 보고서에서 이를 ‘Unity 연결 검색 실패’로 풀어 쓴다. 원본 JSON의 오류 분류·실패 판정·시간은 수정하지 않는다. 연결 검색 실패가 곧 Unity 종료 또는 포트 충돌을 뜻하지는 않는다. 연결 파일을 잠시 읽지 못한 경우에도 발생할 수 있다. [v0.2.0 F02 사례와 확인 범위](DISCOVERY-FAILURE.md)를 참고한다.

한 호출이라도 실패하거나, 요청 수를 다 채우지 못하거나, 마지막 상태가 맞지 않으면 시행 전체를 유효 시간 비교에서 제외한다. 실패 시행의 부분 호출은 상세 자료에 남긴다. 사용자 중단은 Worker 프로세스 묶음을 종료하므로 종료 직전 저장하지 못한 호출까지 반드시 회수되는 것은 아니다. 중단·측정기 오류·정리 실패는 구분한다. 정리가 확인되지 않으면 다음 시행을 실행하지 않는다.

## 수치와 그래프를 읽는 기준

- **유효 완료율** = 유효 시행 / 평가 대상 시행. 평가 대상은 종료 시행에서 환경 준비 실패·벤치 호환성 오류·사용자 중단을 제외한 수다. 미수행도 제외한다. 정리 실패는 포함하고 별도 표시한다. 종료 수·평가 대상 수·제외 사유를 보존하므로 이 값만으로 Bridge 명령 실패율이라고 단정하지 않는다.
- **호출 판정**은 기록된 호출의 성공/실패다. 성공 응답을 받은 호출이 있어도 그 시행의 최종 상태나 정리가 실패할 수 있다.
- **평균·최소·최대·표준편차**는 유효한 새 프로젝트 시행의 대표시간으로 계산한다. 표준편차는 n−1 분모를 쓰며 시행 1개이면 비워 둔다.
- **호출 P95**는 성공한 개별 호출을 정렬해 `ceil(0.95 × 개수)`번째 값을 사용한다. 실패 시행에 남은 성공 호출도 포함한다. 독립 반복의 신뢰구간이 아니며 표본이 적으면 최대값에 가까워진다.
- **부하 처리량**은 유효 S01 시행에서 `요청 수 / 부하 구간 경과 시간`을 구한 뒤 시행끼리 평균한다. 이 구간에는 호출 준비·응답 검증과 공급 간격도 포함된다.
- 세로 시간 그래프의 막대는 각 버전의 유효 시행 평균이다. 최소·최대·변동 폭은 시행 상세에 둔다. 완료율 그래프는 0~100%다. 실패나 미수행을 0ms로 넣지 않는다.
- 앱·SVG의 버전 순서와 색은 실행 기록의 릴리스 순서(기준 버전부터)로 고정한다. 조건·지표를 바꾸거나 측정값이 없어도 같은 버전의 자리와 색을 유지한다.

기존 기록에는 새 오류 종류·개별 호출 판정이 없을 수 있다. 이를 추정해 채우지 않고 ‘분류 기록 없음’·‘판정 없음’으로 표시한다. 두 버전의 직접 비교는 여전히 같은 블록의 공동 유효 시행만 사용하므로 개별 버전 그래프의 평균과 다를 수 있다.

## 이 설계를 택한 이유와 한계

요청 수·동시 요청 수·작업량을 고정하면 어떤 조건에서 지연과 오류가 늘었는지 구분할 수 있다. 작은 echo, 큰 응답, 객체 생성·제거, 컴파일 경로를 나누면 서로 다른 비용을 한 평균에 섞지 않는다. 실패 종류·유효 표본 수를 함께 제시하면 성공한 빠른 호출만 보고 안정적이라고 판단하는 일을 줄일 수 있다.

이는 앱의 실험 설계이며 산업 표준 안정성 인증이 아니다. 기본 동시 요청 4개가 모든 PC에서 CPU·메모리를 포화시킨다는 뜻도 아니다. 더 강한 부하는 같은 총 요청 수·동시 요청 수·입력으로 버전들을 다시 비교해 확인한다. 장시간 메모리 누수, 며칠 단위 가동 신뢰성, 모든 명령의 기능 완전성을 이 시험으로 입증하지 않는다. 호스트 자원과 Windows 캐시는 공유하며 완전한 OS 격리가 아니다. 시간 경계·반복·분리 근거는 [측정 명세](BENCHMARKS.md), [README](../README.md), [로컬 분리 범위](LOCAL-BENCH.md)를 따른다.

오류는 **환경 준비 실패 / 벤치 호환성 오류 / 명령 실행 실패 / 정리 실패**로 구분한다. 이전 기록의 미지원 --no-update-check 원문이 명확한 경우 파생 보고서에서 호환성 오류로 표시하고 평가 분모에서 분리한다. 원본 오류·상태·시간은 변경하지 않는다.
