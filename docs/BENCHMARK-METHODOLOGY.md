# 속도 벤치의 목적·근거·판정 기준

작성일: 2026-09-15. 상태: **VM 기반 속도 벤치의 목표 명세**. VM 제어·새 타이머·예비 기술 통계의 첫 구현을 추가했으며 실제 게스트 통합 검증과 신뢰구간 분석기는 아직 수행·구현 전이다. 현재 사용법은 [BENCHMARKS.md](BENCHMARKS.md), 구현 범위와 남은 검증은 [VM-PILOT.md](VM-PILOT.md)를 따른다. 아래 `draft-v1` 비교는 이전 호스트 배포본을 뜻한다.

## 1. 무엇을 입증하려는가

이 벤치의 질문은 **“같은 PC·가상머신 설정·Unity·입력 조건에서, UnityBridge 릴리스만 바꾸면 올바른 명령 결과를 받는 시간이 얼마나 달라지는가?”**이다. 결과에는 차이의 크기, 시행 간 변동, 실패를 함께 남긴다.

기본 비교 대상은 해당 릴리스의 **CLI + Connector 조합**이다. 두 구성 요소를 함께 바꾼 결과로 CLI 또는 Connector 하나가 원인이라고 단정할 수는 없다. CLI만 비교하려면 Connector 해시를 고정하고 해당 조합의 호환성을 먼저 검증한다. 릴리스에 포함된 빌드 차이도 비교 대상에 포함되므로 특정 소스 수정의 효과를 증명하려면 별도의 통제된 빌드 실험이 필요하다.

RC의 단일 파일→런타임 번들 변경도 이 빌드 차이에 포함한다. 배포 ZIP의 해시와 설치 후 EXE·런타임 전체 해시를 구분해 고정하며 압축 해제는 측정 전 준비 단계에서 수행한다. 같은 시행 안에서 RC 명령마다 ZIP을 다시 풀지 않는다. 자세한 공식 변경과 RC1 버전 보고 예외는 [RC-INSTALL.md](RC-INSTALL.md)에 기록했다.

이 결과가 직접 뒷받침하는 범위는 지정한 명령·작업량·실행 환경이다. AI의 판단 속도, 게임 제작 능력, Unity FPS, 실제 GUI에서의 체감, 모든 PC에서의 성능을 대신 측정하지 않는다.

| 구분 | 이 벤치의 규칙 | 이유 |
|---|---|---|
| 바꾸는 변수 | 선택한 릴리스 조합 | 무엇의 차이를 관찰했는지 분명하게 함 |
| 고정하는 변수 | 호스트·VM 이미지/자원·Unity·프로젝트·도구 소스·명령/작업량·준비 정책·계측기 | 버전 외의 변경이 시간 차이로 섞이는 것을 줄임 |
| 관측하는 결과 | 유효한 명령의 경과 시간, 성공·실패·시간 초과 | 빠르게 잘못 끝난 실행을 개선으로 인정하지 않음 |
| 남는 변수 | 호스트 부하·발열·스케줄링·캐시 등 | 소프트웨어 상태를 복원해도 물리 자원은 공유됨 |
| 주장 범위 | 해당 환경과 명세에서의 조건별 차이 | 한 실험의 결과를 전체 제품 성능으로 확대하지 않음 |

측정 조건을 공개해야 성능 수치가 의미를 가진다는 원칙은 [SPEC CPU 2017 실행·보고 규칙 §1.2.2](https://www.spec.org/cpu2017/Docs/runrules.html)에서도 확인할 수 있다. 여기서는 그 보고 원칙을 참고한다. 이 프로그램이 SPEC 벤치이거나 SPEC 인증을 받았다는 뜻은 아니다.

## 2. 왜 이런 실험을 선택하는가

‘쉬운 게임·중간 게임·어려운 게임’은 AI 생성 코드, 물리 계산, 장면 구성, 성공 기준이 함께 달라져 속도 차이의 해석이 복잡해진다. 속도 전용 범위에서는 **작은 요청, 호출 수, 응답 크기**를 나눠 변화시키는 편이 비교 질문을 명확하게 만든다. 아래 실험 구성과 크기는 이 프로그램의 설계 선택이며 논문이 지정한 표준값은 아니다.

| 실험 | 새 명세에서 수행할 작업 | 확인할 가설 | 대표 지표 | 결과의 한계 |
|---|---|---|---|---|
| F01 첫 호출 | 새 VM 시행에서 Unity ready 확인 후 준비 명령 없이 `echo` 1회 | 릴리스에 따라 처음 명령을 완료하는 시간이 다른가 | ms/첫 호출 | 프로젝트 생성·Unity 부팅 시간, 완전히 비어 있는 하드웨어 캐시를 측정하지 않음 |
| F01 반복 호출 | 별도 VM 시행에서 고정한 준비 호출 W회, 이어서 측정 M회 | 준비 이후 작은 요청의 지연이 다른가 | 시행별 평균 ms/호출, 호출 순서별 원시 시간 | 매번 CLI 프로세스는 새로 시작함. 지속 연결 CLI의 성능이 아님 |
| F02 호출 분할 | 준비 단계에서 오브젝트 1,000개 생성. 같은 1,000개 이동을 1·10·100회로 나눠 순차 요청 | 호출 횟수 증가에 따른 완료 시간과 버전 차이가 어떻게 변하는가 | 전체 이동 구간 ms, 작업 수/초 | 오브젝트 검색·이동 비용도 포함. 순수 통신 비용 또는 동시 처리 한계가 아님 |
| F03 응답 크기 | 1 KiB·64 KiB·1 MiB ASCII 본문을 각 조건에서 동일하게 생성·반환 | 큰 응답에서 시간이 늘어나는 양상이 버전마다 다른가 | 시행별 평균 ms/호출, 실제 stdout 바이트 수 | 본문 생성·직렬화·전송·출력 수집이 포함. 네트워크 대역폭만 측정하지 않음 |

각 버전은 **같은 실험·같은 조건끼리** 비교한다. F02의 호출 수 변화는 별도 실험 요인이다. A 버전의 1회 조건과 B 버전의 100회 조건을 비교해 버전 개선율을 만들지 않는다. F03의 크기도 마찬가지다.

### 공통 도구 `desk_probe`를 사용하는 이유와 제한

현재 F01~F03은 두 버전에 같은 소스의 벤치용 도구를 주입한다. F01의 핵심 명령은 다음과 같다. 실제 실행에는 프로젝트·포트·JSON 출력·업데이트 확인 생략 등 공통 CLI 옵션이 추가된다.

```text
call desk_probe --params '{"action":"echo","nonce":"고정 길이의 요청 식별값"}'
```

도구는 고정값 `42`, 요청 식별값, 프로젝트 경로, Unity 프로세스 ID를 반환한다. 같은 도구 구현을 사용하면 도구 본문의 변화 없이 CLI 실행 → Connector 요청 전달 → 도구 실행 → 응답 수집 경로를 비교할 수 있다.

하지만 이 도구는 릴리스 고유의 장면 편집·콘솔·에셋 처리 도구 본문을 실행하지 않는다. **`desk_probe`가 빨라졌다는 결과만으로 모든 내장 명령이 빨라졌다고 말할 수 없다.** 실제 사용을 설명하려면 두 릴리스에 공통으로 존재하는 내장 명령을 확인한 뒤, 고정 장면 조회나 동일 오브젝트 편집 같은 별도 시나리오를 추가해야 한다. 정확한 명령과 검증 방법을 확인하기 전에는 기본 실험에 포함됐다고 표시하지 않는다.

현재 F02의 이동은 `GameObject.Find`와 Transform 변경을 사용한다. F03은 요청 안에서 문자열을 생성한다. 둘 다 실제 Unity 측 작업이 포함되므로, F01을 빼서 ‘순수 Bridge 처리 시간’을 얻는 계산은 하지 않는다. 여러 구간의 비용이 독립적으로 더해진다고 입증하지 않았기 때문이다. 원인 분석이 필요하면 Connector 내부 계측을 별도 진단 실행으로 추가한다.

## 3. 시간의 시작과 끝을 먼저 고정한다

새 주 지표의 이름은 **게스트 CLI 완료 지연**으로 한다. 게스트의 계측 Worker는 이미 실행된 상태에서 요청 인자·환경·해시·대상을 먼저 확인한다.

```text
VM 복원 → Unity 준비 → 출처·대상 검증 → 준비 호출
                                                ↓
                    [CLI 프로세스 시작 직전 … 종료 + stdout/stderr 수집 완료]
                                                ↓
                               응답 정확성 검증 → 결과 회수 → VM 종료
```

- 시작: 게스트 안에서 CLI의 프로세스 시작 API를 호출하기 직전.
- 끝: 해당 CLI가 종료되고 stdout/stderr를 끝까지 수집한 시점. 성공 판정은 뒤에서 수행한다.
- 포함: CLI 시작·실행, 접속, Connector와 도구 처리, 출력 생성·파이프 수집, 그 사이의 대기.
- 제외: VM 부팅, 다운로드/해시 검증, Worker 기동, 프로젝트 적용/컴파일, 준비 호출, 최종 응답 검증, 호스트로 결과 전송.
- 준비·검증·정리 시간도 별도 저장한다. 사용자가 기다리는 전체 시간과 명령 속도를 각각 확인할 수 있게 한다.

시작·끝은 **같은 게스트, 같은 시계**로 잰다. 호스트에서 받은 시각과 게스트에서 보낸 시각을 빼지 않는다. Microsoft는 같은 시스템 또는 VM의 작은 시간 간격에 QPC 사용을 권장하며, QPC는 시스템 시각 변경과 독립적이라고 설명한다. 구현은 이를 사용하는 게스트 계측 경로와 시계 주파수를 확인한다. [Microsoft 고해상도 시간 측정 문서](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)

QPC를 사용해도 호스트가 VM 실행을 지연시킨 시간이 없어지지는 않는다. 이 지표는 CPU가 실제로 연산한 시간만이 아니라 **완료까지의 경과 시간**이다. 측정 중 VM 일시정지·저장·복원·이동은 허용하지 않는다.

F02의 주 지표는 첫 이동 CLI 시작 직전부터 마지막 이동 CLI의 종료·출력 수집까지의 **연속 구간 전체 시간**이다. 호출 사이의 Worker 제어 비용도 포함하고, 호출별 지연의 합은 보조 지표로 따로 저장한다. 현재 `workMs`는 호출별 시간의 합이므로 새 F02 전체 구간 지표와 같지 않다. 처리량은 `1,000 / 전체 구간 초`로 계산하며 동시 요청은 사용하지 않는다.

계측 중 출력은 제한된 메모리 버퍼에 모으고 UI·호스트로 본문을 실시간 전송하지 않는 구조를 제안한다. 출력 수집 자체의 비용은 포함하되 로그 표시나 결과 파일 쓰기가 추가 병목을 만들지 않도록 계측기 버전과 출력 제한을 고정한다. 무작업 자식 프로세스와 알려진 대기·출력을 가진 진단 프로그램으로 구간과 계측 비용을 확인하되, 그 시간을 모든 결과에서 일괄 차감하지 않는다.

### 현재 배포본과 달라지는 점

| 항목 | 현재 `draft-v1` | 새 VM 명세 제안 |
|---|---|---|
| 실행 위치 | 호스트의 새 프로젝트 복제본·새 Unity 프로세스 | 복원한 게스트 OS 안의 Unity·CLI·Worker |
| 타이머 | `FixedExperiments.Raw`가 `BridgeAdapter.CallAsync` 전체를 감쌈 | 게스트에서 CLI 시작 직전부터 종료·출력 수집까지 |
| 포함된 보조 비용 | 인스턴스 검색, EXE 해시, 매 호출 Worker 시작, 출력 중계/JSON 처리, 대상 재확인 | 해당 준비·검증·중계 비용을 주 지표 밖으로 분리 |
| F02 주 시간 | 개별 호출 시간 합 | 이동 명령열의 연속 완료 시간 |
| F03 | 해당 크기 1회 호출 | 크기별 준비 정책과 측정 호출 수를 고정한 반복 조건 |
| 결과 분석 | 독립 시행의 기술 통계, Pilot | 예비 시험 후 고정한 계획·효과 크기·불확실성 보고 |

따라서 새 계측기에는 별도 `measurementSchema`를 부여한다. 이전 결과를 VM 결과로 바꾸어 표시하거나 새 결과와 합산하지 않는다. 현재 코드 근거는 문서 끝에 연결했다.

## 4. VM을 쓰는 논거는 ‘이전 시행의 상태를 되돌리기’다

폴더 복제만으로는 사용자 프로필, TEMP, 레지스트리, 다른 폴더의 Unity 캐시까지 초기화하지 못한다. 독립 시행마다 **정상 종료한 공통 기준 이미지**로 게스트의 쓰기 상태를 복원하면 이전 버전 실행의 덤프·임시 파일·설정 변경이 다음 버전에 전달되는 경로를 줄일 수 있다.

Oracle 문서상 일반 모드의 가상 디스크는 스냅샷 복원 시 이전 상태로 돌아가지만, 디스크 모드에 따라 동작이 다르다. 실행 중 스냅샷은 메모리 상태도 보존할 수 있다. 따라서 본 설계는 복원 대상인 쓰기 디스크만 연결하고, **Unity가 실행 중인 메모리 스냅샷을 기준으로 사용하지 않는다.** [Oracle 스냅샷 설명](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/working-with-vms.html), [가상 디스크 쓰기 모드](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/storage.html)

VirtualBox 제어기를 이 복원 방식으로 구현했다. 실제 설치된 VM 엔진과 Unity 게스트 실행은 사전 시험으로 검증해야 한다.

| 구분 | 설계 규칙 | 실제로 남길 증거 |
|---|---|---|
| 공통 출발 상태 | 한 기준 이미지에서 매 독립 시행 시작, 안정적인 VM 식별자 유지 | 이미지/스냅샷 ID·지문, 부팅·복원 기록 |
| 잔여 파일 | TEMP·AppData·작업 폴더·시험 레지스트리 표식이 복원 후 사라져야 함 | 이전 시행 표식과 다음 시행 검사 결과 |
| 입력만 전달 | 해시가 고정된 릴리스·프로젝트·도구 소스만 전달 | 입력 명세, 실제 CLI/Connector/도구 해시 |
| 외부 상태 유입 | 호스트 홈/프로젝트 공유, 클립보드, 영구 쓰기 디스크를 시험에 연결하지 않음 | VM 연결 장치·공유 설정 목록 |
| 복원 실패 | 다음 시행 중단. 호스트 실행으로 자동 전환하지 않음 | 명시적 격리 실패 상태 |

**VM은 환경 의존성을 없애지 않는다.** 호스트 파일 캐시 때문에 두 번째 VM 실행의 디스크 접근이 빨라질 수 있다는 설명도 Oracle 문서에 있다. 호스트 CPU·저장장치·스케줄러를 공유하므로 결과의 범위는 같은 PC와 VM 설정에서의 비교다. [Oracle 호스트 I/O 캐시 설명](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/storage.html)

한 번에 VM 하나만 실행하고 CPU·RAM·디스크 컨트롤러·호스트 캐시 설정을 고정한다. 할당 RAM은 게스트 메모리 압박과 호스트 페이징을 함께 확인해 정한다. 다운로드·보고서 생성은 측정 밖에서 수행한다. 호스트 부하·전원 상태·가용 메모리와 관측 가능한 게스트 부하를 기록하고, 읽지 못한 항목은 미제공으로 둔다. VM 결과를 네이티브 Windows의 절대 속도로 환산하는 보정 계수는 만들지 않는다.

## 5. ‘첫 호출’과 ‘준비 이후’를 섞지 않는다

첫 호출은 **새 시행의 Unity 기동·컴파일이 끝나고 Connector가 ready를 표시한 후, Bridge 준비 명령 없이 보내는 첫 명령**이다. ready 여부는 연결 정보로 확인하고 그 전에 `echo` 또는 다른 CLI 명령을 보내지 않는다. ready 확인 시각과 첫 명령 시작 시각의 간격도 기록한다.

이 과정에서 설치·컴파일·해시 읽기가 이미 일어났으므로 OS/디스크 전체가 차갑다는 뜻이 아니다. 화면에는 ‘콜드’만 쓰지 않고 **Unity 준비 후 첫 호출**이라고 표시한다.

반복 조건은 별도 시행에서 시작하며 준비 횟수 W와 측정 횟수 M을 실행 전 고정한다. F01은 같은 `echo`, F03은 해당 크기의 같은 `payload`를 준비 호출에도 사용한다. F02는 오브젝트 생성 뒤 고정한 `echo` 준비를 거친 다음, 측정 대상 이동을 한 번씩 수행한다. 이 순서 자체도 실험 명세의 일부다.

W는 모든 버전의 예비 호출 추이를 관찰해 정하고 본시험에서는 바꾸지 않는다. 빠른 표본만 남기려고 앞부분을 뒤늦게 버리지 않는다. 준비 뒤에도 시간이 계속 변하면 ‘안정 상태’라고 이름 붙이지 않고 ‘W회 준비 이후’ 결과와 순서별 추이를 보고한다. CLI는 항상 새 프로세스이며, 재사용하는 것은 해당 시행의 Unity 세션과 그 안에서 형성된 상태다.

초기·반복 실행의 변동을 나눠 살펴야 한다는 연구 방법론을 이 구조에 적용한다. Java 런타임을 연구한 논문에서 말하는 VM 실행과 여기의 게스트 OS 스냅샷 복원은 같은 기술이 아니다. [Kalibera·Jones, 2013](https://kar.kent.ac.uk/33611/)

## 6. 반복과 실행 순서의 근거

분석에서의 독립 시행 단위는 **기준 VM 복원 → 해당 버전 준비 → 그 조건 측정 → 종료** 한 번이다. 같은 Unity 세션에서 100회 호출해도 독립된 환경 시행 100회가 되지 않는다. VM 복원 또한 통계적 독립을 자동 증명하지 않으므로 시행 순서의 추세·자기상관을 점검한다.

예를 들어 A/B 버전을 각각 10번 복원하고 시행마다 20회 호출하면 버전별 원시 호출은 200개, 독립 시행은 10개다. 같은 반복 번호의 A/B를 비교하는 블록도 10개다. 반복 호출의 대표값은 각 시행의 평균으로 만들고 시행들에 같은 가중치를 준다. 일부 호출이 실패하면 그 시행의 완료 조건부터 판정하며 성공 호출만 주워 모아 정상 시행으로 만들지 않는다.

시간이 흐르는 동안 PC 상태가 바뀌는 영향을 줄이기 위해, **같은 실험·조건에서 가까운 시간에 실행하는 모든 비교 버전**을 한 블록으로 묶는다. 두 버전이면 AB와 BA의 개수를 균형 있게 배치하고 그 블록 순서를 기록한 난수 시드로 섞는다. 세 버전 이상도 위치가 한쪽에 치우치지 않게 배치한다. 새 버전의 모든 시행을 항상 마지막에 몰아두지 않는다.

이는 유사한 조건끼리 묶고 남은 영향을 무작위화하는 [NIST의 블록 실험 원칙](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)을 적용한 설계다. 순서 교대만으로 모든 편향이 사라지는 것은 아니다. 평범해 보이는 설정도 성능 결론을 바꿀 수 있다는 [Mytkowicz 외, 2009](https://sape.inf.usi.ch/publications/asplos09.html)의 연구는 그 한계를 점검할 근거다. 해당 논문이 UnityBridge에 편향이 있다고 실측한 것은 아니다.

### 반복 수를 정하는 절차

1. **연결 확인:** 기존 2회 반복은 실행 흐름과 결과 검증용이다. 개선을 확정하는 근거로 쓰지 않는다.
2. **예비 시험:** 버전별 호출 순서와 시행 간 변동, VM 준비 비용을 모은다. 같은 버전을 A/A로 비교하는 점검도 포함해 한쪽 위치만 일관되게 유리한지 본다. A/A 통과가 모든 오차가 없다는 증명은 아니다.
3. **본시험 계획 고정:** 구별하려는 최소 차이와 허용할 신뢰구간 폭, 시간 예산을 정한다. 예비 자료의 시행 간 변동을 사용해 독립 반복 수 N과 시행 내 호출 수 M을 산정한다. W·N·M, 중단/제외 규칙, 분석법과 난수 시드를 저장한다.
4. **본시험:** 정한 수를 수행한다. 좋은 결과가 나왔다는 이유로 조기 종료하지 않는다. 시간 예산으로 계획을 끝내지 못하면 미완료로 보고한다.
5. **정밀도 확인:** 구간이 너무 넓으면 ‘차이 판단 보류’다. 추가 시험은 변경 사유와 새 계획을 남기고, 유리한 실행만 골라 합치지 않는다.

변동이 주로 시행 사이에서 생기면 같은 시행의 호출만 늘리기보다 VM 복원 횟수를 늘려야 한다. 반복을 어느 수준에 배분할지와 효과 크기의 불확실성을 보고하는 방법은 [Kalibera·Jones의 연구](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf)를 참고한다. **‘30회면 충분하다’ 같은 보편적인 수는 이 연구로 보장되지 않는다.**

범위가 커지면 비용도 드러내야 한다. F01 2조건 + F02 3조건 + F03 3조건을 두 버전에서 독립 N회씩 실행하면 VM 시행은 `8 × 2 × N`번이다. 앞의 10회는 계산 예시이며 확정된 기본값이 아니다.

## 7. 결과 판정 규칙

먼저 전체 계획 수·시도 수·정상 완료·응답 오류·시간 초과·취소·환경 실패를 구분한다. 실패는 0ms로 넣지 않고, 제한 시간도 정상 완료 시간으로 바꿔 넣지 않는다. 실패 전 부분 측정과 경과 시간은 진단용으로 보존한다. 재시도는 새 시도로 연결하고 기존 실패를 덮어쓰지 않는다.

정상 완료의 조건은 CLI 정상 종료, 출력 완전성, 이번 nonce·대상 프로젝트·PID·실제 버전 일치, 실험별 최종 결과 통과다. F02는 오브젝트 개수·유일 ID·최종 위치를, F03은 전체 ASCII 본문을 검증한다. ‘속도만 측정’해도 이 검증은 필수다. 정답 확인을 성능 실행에 함께 요구하는 사례는 [SPEC 실행 규칙 §3.1·§3.2.2](https://www.spec.org/cpu2017/Docs/runrules.html)에 있다.

속도 표에는 **성공한 시행에 조건부인 시간**임을 표시한다. A/B 비교 추정에는 두 버전이 모두 정상 완료한 블록만 사용하고, 전체 블록 중 빠진 수와 이유를 함께 보여준다. 실패가 있는 상태에서 이 값만으로 B가 전반적으로 더 낫다고 판정하지 않는다. 준비 실패·응답 실패·정리 실패도 숨기지 않으며 격리가 확인되지 않으면 이후 시행을 중단한다.

| 결과 항목 | 계산·표시 원칙 |
|---|---|
| 주 시간 | F01/F03은 시행별 평균 ms/호출, F02는 시행별 전체 작업 구간 ms |
| 절대 차이 | 같은 조건의 블록별 `B 시간 − A 시간`을 평균. 음수면 B가 짧음 |
| 시간 감소율 | 같은 유효 블록의 평균 시간으로 `100 × (1 − 평균 B / 평균 A)` 계산. 분모와 기준 버전 표시 |
| 배속 | 필요하면 `평균 A / 평균 B`를 별도로 표시. ‘시간 20% 감소’와 ‘1.2배 빠름’을 혼용하지 않음 |
| 변동 | 시행별 점, 평균·중앙값·범위, 유효 시행/블록 수, 차이의 신뢰구간 |
| p95 | 기본 숨김. 호출 지연인지 시행 평균인지 정의하고 꼬리 구간 추정의 표본 수·불확실성을 검토한 경우만 제공 |
| 종합 점수 | 기본 제공하지 않음. 서로 다른 실험의 단위와 질문을 임의로 합산하지 않음 |

새 분석의 제안은 블록의 A/B 쌍을 함께 재표집해 절대 차이와 감소율의 **95% 신뢰구간**을 계산하는 방식이다. 시행 내 개별 호출을 독립 표본처럼 재표집하지 않는다. 분석기·재표집 횟수·난수 시드는 본시험 전에 고정한다. 작은 블록 수에서는 재표집을 많이 해도 근거가 늘지 않으므로 예비 시험에 확정 판정을 붙이지 않는다. 시간 추세가 크거나 블록 간 의존이 보이면 그 실행에 독립성 가정을 그대로 적용하지 않고 환경/계획을 재검토한다. 이 분석기는 아직 구현·검증 전이다.

구간이 시간 차이 0 또는 감소율 0을 걸치면 개선을 확정하지 않는다. 이것은 두 버전이 같다는 증거도 아니다. 차이가 관측되더라도 실용적으로 의미 있는지는 실행 전에 정한 최소 차이와 함께 판단한다. 여러 조건 중 유리한 한 셀만 골라 ‘전체 개선’이라 하지 않는다. 개별 95% 구간이 모든 조건을 동시에 95% 보장하는 것도 아니다.

큰 값이라는 이유만으로 표본을 삭제하지 않는다. 사전 정의한 환경 위반은 제외 사유와 원시 기록을 남기고, 실제 제품 지연·시간 초과는 제품의 결과로 보존한다.

## 8. 결과와 함께 남길 재현 자료

- 계획 ID·명세 버전·계측기/분석기 해시, 전체 명령/공통 옵션, 실험 크기·W/N/M·제한 시간·검증 기준.
- 저장소·릴리스 태그·자산 URL·소스 커밋, CLI와 Connector 및 공통 도구의 실제 해시. 로컬 계산 해시와 게시자 제공 검증값은 구별한다.
- 호스트 OS/CPU/자원, VM 엔진/버전·가상 CPU/RAM·디스크/캐시 설정·이미지 지문, 게스트 OS/Unity/런타임 버전, Unity 기동 옵션.
- 블록/시행 ID·실행 순서·난수 시드·실제 프로세스/프로젝트·ready 시각·요청 식별값·상태·출력 크기·원시 시간.
- 준비/작업/검증/정리의 시간, 전체 성공/실패/중단 수, 제외 사유, 분석에 사용한 블록 목록.

독립 실행의 결과를 다시 계산할 수 있게 원시 JSON/CSV와 요약을 연결한다. 실행 중 릴리스의 `latest`를 다시 해석하지 않는다. 명세·환경·계측 구간이 다른 자료는 같은 표본 집합으로 합치지 않는다. 공개 내보내기는 인증 정보와 개인 경로를 제거하되 대상 동일성을 확인할 익명 식별자를 유지한다.

보고 문장의 형식은 다음과 같다. 대괄호 항목은 실제 결과가 들어갈 자리이며 성능 결과를 미리 만들어 두지 않는다.

> [호스트/VM/Unity/명세]에서 [작업·조건]을 비교했다. 전체 [N]블록 중 두 버전 모두 성공한 [n]블록에서, B의 평균 완료 시간은 A보다 [x]ms, [y]% 짧았다. 감소율의 95% 신뢰구간은 [하한, 상한]이며 실패·시간 초과는 A [a]건, B [b]건이다. 이 결과는 지정한 작업과 환경에 한정된다.

## 9. 명세가 성립하는지 먼저 검증한다

| 사전 점검 | 통과 근거 |
|---|---|
| 실제 게스트 연동 | VM 안의 Unity·CLI·Connector가 지정 버전으로 실제 명령을 수행하고 응답의 PID/프로젝트가 일치 |
| 복원·오염 차단 | 정상 종료와 강제 종료 뒤 모두 이전 시험 표식이 제거됨. 복원 실패를 주입하면 다음 시행이 시작되지 않음 |
| 측정 경계 | 해시 확인/Worker 준비/호스트 전송에 의도적 지연을 넣어도 주 시간이 직접 늘지 않고, 측정 구간 내 지연은 반영됨 |
| 응답·실패 검증 | 잘못된 nonce/본문/위치, 잘린 출력, 시간 초과가 정상 속도 표본에서 제외되고 실패 건수에 남음 |
| 집계 검증 | 합성 자료로 시행 평균·F02 구간·쌍 비교·누락 블록이 명세대로 계산됨. 신뢰구간은 알려진 분포/모의 반복으로 성질을 확인 |
| A/A 예비 시험 | 동일 릴리스를 두 라벨/실행 위치로 비교하고 순서와 환경의 편향 여부를 관찰 |

합성 검사는 계측기의 정확성을 검증한다. 실제 Unity 실행이나 릴리스의 속도 차이를 입증하는 자료로 사용하지 않는다. 위 점검과 예비 시험을 마친 뒤 기준 VM 자원, W/N/M, 최소 의미 차이·목표 정밀도를 본시험 계획에 고정한다.
