# v0.4.0 검증 기록

검증일은 2026-09-17이다. 자동 검사, 실제 Unity 연동 검사와 성능 우열을 판단하는 본 측정을 구분한다.

## 자동 검사

Release 빌드 경고 0개·오류 0개, `build/Verify.ps1` 자동 검사 **216개 통과**를 확인했다. Core 38개, Infrastructure 150개, Desktop 28개이다. 테스트 호스트 종료 과정의 미처리 예외도 확인했다.

이번 추가 검사는 고정 exec 소스 해시, nonce 분리, 동시 요청 제한, 요청별 한 번 실행, 시간 초과 후 신규 투입 중단, 취소 시 부분 기록, 기대 결과의 객체 필드 비교, 오류 분류, 시행·호출 분모, P95·처리량, 결과 메타데이터 검증과 그래프를 포함한다. 기존 파일·프로세스 정리, 릴리스 설치, 구버전 결과, TXT·Excel 출력 검사도 유지했다.

그래프 수정 후에는 측정 순서가 조건마다 바뀌는 3개 버전의 계획으로 표시 순서·색 고정을 검사했다. 실패·미수행·계획에 해당 버전이 없는 조건에서도 자리를 유지하고, SVG도 같은 순서·색을 쓰는지 확인했다. 형식 4 보고서를 형식 5로 새 사본 생성하는 검사까지 4개를 추가했다. 이 수정은 표시·내보내기 변경으로, 실제 Unity 벤치를 다시 수행하지 않았다.

화면 검사 중 설정 저장이 동기적으로 완료되면 Closing 처리 안에서 다시 Close를 호출하는 오류가 재현되었다. 다음 UI 작업으로 닫기를 넘겨 재진입을 막았고 전체 검사를 다시 통과했다. WPF 결과 화면과 작은 창·150% 배율, 그래프 지표 전환, 기존 메뉴·표·큰 시계를 확인했다.

UI 개편에서는 합성 기록으로 예정 시행 수의 즉시 갱신, 실제 진행 이벤트의 종료 수 표시, 완료 후 선택 탭 유지, 늦게 도착한 진행 이벤트 무시와 정리 실패 표시를 확인했다. 작은/일반 창의 100·150·200% 렌더링, 메뉴 열기·Escape 닫기, 벡터 마스코트와 48px 시계도 확인했다. 벤치 재실행이나 새 성능 판정은 수행하지 않았다. 진행 이벤트는 측정기의 생명주기를 전달하며 CLI 계측 구간과 계산식을 바꾸지 않는다.

테마 배경 연동에서는 기존 화면 검사에 저장된 민트 테마의 시작 복원, 연보라·로즈·민트의 서로 다른 내장 이미지 전환, 색상·배경의 동시 적용, 메뉴의 현재 테마 표시, 선택 탭 유지와 연속 클릭의 마지막 선택 저장을 추가했다. 세 테마의 실제 WPF 화면을 렌더링해 확인하고, 다시 선택한 배경은 디코딩된 이미지를 재사용하는지도 확인했다.

## 실제 Unity 연동

연결 검색 오류 표시 수정에서는 실제 Unity 벤치를 다시 실행하지 않았다. 표준 출력/표준 오류의 CLI 실패 응답, 시간 초과 우선 분류, 표준 오류의 성공 응답 거부, 기존 실패 원문 보존, 19번째 실패·18개 성공 표시와 형식 4·5 보고서의 형식 6 전환을 검사했다. 수정하지 않은 v0.2.0·v0.2.1 클라이언트에 파일 읽기 충돌을 주입한 재현과 실제 저장 기록의 관찰은 [연결 검색 실패 확인](DISCOVERY-FAILURE.md)에 따로 정리했다.

환경은 Windows, Unity **6000.5.4f1**, 공식 UnityBridge **0.2.1·0.2.3**의 캐시된 CLI·Connector 조합이다. 실행 전 내용 해시를 검사했다. 원래 개인 프로젝트 대신 새 시험 프로젝트를 사용했다.

| 조건 | 설정 | 확인 결과 |
|---|---|---|
| F04 first / prepared | 버전별 N=1, W=1, M=2 | 4개 시행 성공 |
| S01 기본 5개 시나리오 | 버전별 N=1, 요청 4개·동시 2개 | 10개 시행 성공 |
| 전체 정리 | 새 프로젝트·프로세스·임시 폴더 | 14개 시행 모두 확인 |

총 46개 측정 호출이 기록되었다. 준비 호출은 이 수에 포함하지 않는다. 실행 ID는 `dc12b0cf-eb3e-4b84-99bf-48b38235ea18`이다. F04 소스 SHA-256은 `1cf0372924830e506ce9f27a468db18a334e8a70796ca409794b5f465b44f881`로 일치했다. 해당 원본에서 TXT·분석 Excel·실패 내역·SVG를 생성했다.

처음에는 제한된 실행 환경에서 Unity 라이선스 설정 경로 접근이 거부되어 준비가 진행되지 않았다. 측정 전에 시도를 중단하고 시험 프로세스 종료·소유 폴더 복구 후, Unity 설정에 접근 가능한 실행 환경에서 위 검사를 수행했다. 접근 실패 시도를 정상 성능 표본에 포함하지 않았다.

## 사용자 명령·오류 경로 확인

같은 환경에서 요청 4개·동시 2개로 추가 8개 시행을 수행했다. 실행 ID는 `d5860dc7-9b7c-4fad-be54-90944a69537e`이다.

| 시나리오 | 두 버전의 실제 결과 |
|---|---|
| 사용자 exec: 1~1,000 합산, 기대값 500500 | 2개 시행 성공 |
| 잘못된 C# 문법 | 2개 시행 CLI 종료 오류로 기록 |
| 실제 반환값 42, 기대값 43 | 2개 시행 응답 불일치로 기록, 신규 요청 투입 중단 |
| 없는 명령 이름 | 2개 시행 명령 미지원으로 기록, 신규 요청 투입 중단 |

모든 시행에서 시험 폴더 정리를 확인했다. 오류 시행은 유효 시간 평균에서 제외하고 부분 호출과 이유를 결과에 남겼다.

잘못된 C# 문법에서는 기대했던 구조화된 `Compile error` 응답 대신, 공식 CLI의 `UnicodeEncodeError: cp949 ... U+FFFD`와 종료 코드 1이 관찰되었다. stdout에 JSON이 없어 실제 판정은 `cli-error`이다. 따라서 실환경에서의 **컴파일 오류 세부 분류까지 성공했다고 주장하지 않는다.** 정상 JSON으로 반환되는 Compile/Runtime error 분류는 합성 자동 검사로 확인했고, 실제 CLI 출력 인코딩의 한계는 그대로 보존했다. 이 추가 확인의 기대 분류 검사에서는 해당 2건이 기대한 compile-error와 달랐다.

## 확인 범위

위 수치는 기능 연동 검사다. 기본 부하 설정인 요청 32개·동시 4개나 최대 설정까지 실제 부하를 가한 결과가 아니다. 작은 반복 수로 버전의 속도·안정성 우열을 결론 내리지 않는다. 고부하 본 측정은 같은 호스트 상태·입력·횟수·동시 요청 설정으로 별도로 수행해야 한다.

다른 Unity/Bridge 버전, 모든 내장·사용자 도구, GUI/Play Mode 의존 명령, 오랜 시간의 메모리 누수와 다양한 PC 환경은 포괄 검증하지 않았다. 실제 Windows 정책·라이선스 상태에 따른 실행 가능성도 달라질 수 있다. GitHub Actions는 업로드 후 별도 실행이 필요하다.

## 2026-09-18 · 결과 화면 스크롤 수정

수정 전 실제 WPF 그래프에 휠 이벤트를 전달해 결과 화면의 스크롤 위치가 0에서 움직이지 않는 문제를 재현했다. 가로 스크롤 전용 그래프와 내용이 모두 보이는 표·텍스트가 휠 이벤트를 소비하므로, 내부에서 더 스크롤할 수 없는 방향의 입력을 바깥 결과 화면으로 전달한다.

960×600과 1230×800에서 그래프·시간 표·비교 표·안정성 표·시행 설명·요약 메모 위의 위아래 스크롤을 검사했다. 긴 시행 표는 내부 스크롤을 유지하고 맨 위·아래에서만 바깥 화면으로 이어지는지 검증했다. Desktop 테스트 28개가 통과했다. 벤치 측정 로직과 저장된 결과는 변경하지 않았으며 실제 Unity 벤치를 실행하지 않았다.

## 2026-09-18 · 공식 Unity CLI + Pipeline 비교

UI 변경 없이 공식 도구 어댑터와 비교 실행 진입점을 추가했다. `build/Verify.ps1`에서 Release 빌드 경고·오류 0개, Core 38개·Infrastructure 165개·Desktop 28개, 총 231개 자동 검사와 테스트 호스트 정상 종료를 확인했다. 새 검사는 명령 인수 분리, 중첩 eval 응답의 내부 실패, 대상 식별, 이전 JSON 호환성, 다운로드 해시·패키지 경로 보호, Editor 내장 의존 패키지 고정, 잘못된 PID·오래된 준비 파일·포트 변경 거부를 다룬다.

실제 연동 환경은 Windows, Unity **6000.3.23f1**, UnityBridge **v0.2.1**, 공식 Unity CLI **1.0.0-beta.10**, Pipeline **0.7.0-exp.1**이다. 공식 CLI의 게시 SHA-256은 `2ac041e4fa04e7bedca1d53cc059981c323ae430aafaafdb8defd7f70a58ba81`이다. 원래 프로젝트 대신 별도 임시 데이터 루트의 새 프로젝트를 사용했다.

- F01: N=1, W=0, M=1에서 두 도구의 first/prepared 4개 시행을 확인했다. 실행 ID는 `7683a581-8b26-4641-b310-474807ae044c`다. 이 실행의 F04 공식 대상 2건은 당시 중첩 응답 해석 오류로 제외됐으므로 이 실행 전체를 성공으로 표시하지 않는다.
- F04 수정 후 재확인: N=1, W=1, M=1에서 두 도구의 first/prepared **4개 시행 모두 성공·정리 완료**를 확인했다. 실행 ID는 `b3e587f3-2769-4989-bcf5-b6fced3aa87f`다. 두 도구의 C# 소스 SHA-256은 `1cf0372924830e506ce9f27a468db18a334e8a70796ca409794b5f465b44f881`로 같았다.
- F02·F03·S01: N=1, W=1, M=1, 부하 요청 4개·동시 2개로 **22개 시행·268개 측정 호출 모두 성공**을 확인했다. 실행 ID는 `f55c17bd-d29e-4f65-a933-08cd4f27ea3c`다. F02의 1·10·100개 명령, F03의 1 KiB·64 KiB·1 MiB, S01의 공통 5개 시나리오를 두 도구에서 실행했다. 시험 Worker·Editor 종료, 임시 프로젝트 정리, TXT·Excel·SVG 보고서 생성을 확인했다.

최종 확인 범위는 위 F01 4개, 재시험 F04 4개, F02·F03·S01 22개를 합친 **30개 성공 시행·276개 측정 호출**이다. 준비 호출은 제외했다. 원시 결과와 보고서 복사본은 개발 폴더 `.cache/official-comparison-validation/20260918`에 보관하며 공개 소스·배포 ZIP에는 포함하지 않는다.

개발 중 첫 시도에서는 Unity 6000.3에 Test Framework 1.1.33을 강제 적용한 API 불일치와 깊은 Windows 경로의 DLL 로드 오류를 확인했다. Editor 내장 의존 버전을 고정하고 짧은 시험 루트에서 재확인했다. 이후 발견한 Pipeline의 중첩 eval 응답 처리 오류는 어댑터 수정과 자동·실환경 재시험으로 확인했다. 이 개발 실패들은 성능 표본으로 재분류하거나 삭제하지 않았다.

이 확인은 연동 검사다. 반복 1회 결과로 속도·안정성 우열을 주장하지 않으며, 다른 Editor·CLI·Pipeline 버전과 최대 부하 범위의 호환성까지 입증한 것은 아니다. 실행 설정, 공통 작업과 한계는 [공식 Unity 비교](OFFICIAL-UNITY-COMPARISON.md)에 기록한다.

## 2026-09-18 · 앱 버튼에서 공식 비교 실행
