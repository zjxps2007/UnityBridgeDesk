# 연구용 검증과 실험 계획

2026-09-21. v0.5.0 이후 보완이다. 이번 기능은 측정기의 한계를 확인하고 연구 자료를 보존하는 수단이다. 논문 사용 인증이나 모든 환경의 정확성 보증은 아니다. 기존 실제 Unity 연동 기록과 이번 합성 검증은 구분한다.

이번 추가된 지연 감지, 조건 순서 무작위화, 세션 기록, 전체 실행기 명세, F02 외부 정답 검사와 새 UX는 [연구 검증 보완](RESEARCH-EXTENSIONS.md)에 명세한다. 아래 최초 구현의 제한과 구분해 읽는다.

## 앱에서 사용하는 순서

준비 → **실험 목적**에서 탐색·예비·본시험·A/A·알려진 지연 감지를 선택하고 **연구 계획·세션 기록**을 펼친다. 최신 동작·파일 명세·정답 검사는 [보완 사용법](RESEARCH-EXTENSIONS.md)을 기준으로 한다. 연구 질문과 허용 차이를 정한 이유를 작성한다. 본시험과 A/A는 새 프로젝트 5회 이상이며 대상 수의 배수여야 시작할 수 있다. 이 하한은 통계적 충분성을 보장하지 않는다.

**A/A**는 UnityBridge 릴리스 하나만 선택한다. 공식·Go 도구 선택은 끈다. 같은 원본의 CLI·Connector·런타임 해시·커밋을 갖는 `[A]`, `[B]` 대상으로 서로 다른 프로젝트·Unity 프로세스·시행 ID를 사용한다. 기존 표본을 복사하지 않는다. 원본 릴리스 태그는 SourceTag로 보존해 RC의 버전 보고 예외까지 원래 규칙으로 검사한다. 기본 실행기·타이머·검증·정리를 그대로 사용한다. 다른 제품의 A/A는 아직 지원하지 않는다.

A/A 허용 차이는 시간비 B/A의 ±범위다. 1%는 입력 예시이며 논문·인증 기준이 아니다. 연구에서 의미 있는 최소 차이와 허용할 측정 영향을 고려해 시작 전에 이유를 적는다. 감소율로 표시하는 화면과 시간비의 경계를 혼동하지 않는다.

판정에는 사전 고정 계획 일치, 같은 원본, 완료·제외 없는 유효 쌍, 유한한 95% 시간비 구간이 필요하다. 20쌍 미만이거나 시행 순서 신호가 있으면 판단을 유보한다. 20쌍은 현재 순서 진단을 수행하기 위한 앱의 하한이며 충분성 증명이 아니다. 구간 전체가 사전 허용 범위 안이면 그 조건에서만 일치 근거를 표시한다. 구간 전체가 범위 밖이면 차이 관찰, 경계에 걸치면 검증 불충분이다. 구간에 0% 감소가 포함된다는 이유만으로 동등하다고 하지 않는다. 여러 조건 전체의 동등성에 대한 다중 비교 보장은 없다.

## 시작 전에 고정하는 내용

일반 탐색 실행도 첫 시행 전에 `frozen-plan.json`, `frozen-plan.sha256`를 결과 폴더에 저장한다. 같은 원문·해시를 run.json에도 포함한다. 실행 ID, 옵션·연구 질문·허용 차이·진행 갱신 정책, 대상 순서·실제 시행 순서, 소스 커밋·배포 해시, Editor, fixture·Worker 해시, 앱 버전·환경·시간 경계·제외 규칙·분석 규칙을 담는다. 각 시행 직전에는 기존 메모리 기록에 활성 전원 구성 GUID를 추가한다. 전원 설정을 바꾸거나 CPU 온도·클럭을 통제하지 않는다.

결과에서 계획 원문의 SHA-256과 실행 설정·대상·순서를 대조한다. 결과가 쌓이거나 정상 중단된 것은 계획 변경이 아니다. 설정이나 원문이 바뀌면 불일치로 표시한다. 로컬 파일과 해시는 외부 사전등록·디지털 서명·변조 방지 저장소를 대신하지 않는다. 파일 작성·검사는 명령 측정 밖에서 수행한다.

예비 실험의 호출 순서·분산·비용을 보고 다음 실험을 설계한다. 본시험 표시를 선택하는 것만으로 설계가 타당해지는 것은 아니다. 실행 도중 유리한 신뢰구간이 나올 때 멈추지 않으며, 취소·정리 실패 등 안전상 중단은 그대로 기록한다. 과거 run.json에 없던 사전 계획을 뒤늦게 생성해 사전등록으로 표시하지 않는다.

## Unity 없이 계측 확인

같은 패널의 **Unity 없이 실행기 진단**은 Worker 자체의 진단 자식 프로세스를 사용한다. 0·25·100ms 대기를 각 20블록, 총 60회 실행한다. 고정 시드로 블록 안 순서를 섞는다. 정상 벤치와 같은 TimedProcessRunner로 프로세스 시작부터 종료·출력 수집까지 측정한다. 요청 nonce와 실제 자식 내부 경과 시간을 확인하며 요청한 대기 시간이 정확하게 실현됐다고 가정하지 않는다.

잔차는 `(지연 조건 외부 시간 − 0ms 조건 외부 시간) − (지연 조건 실제 내부 시간 − 0ms 조건 실제 내부 시간)`이다. 잔차 평균과 쌍 단위 t 구간을 진단용으로 저장한다. 음수 잔차도 보존하며 앱의 속도 통계에서 임의로 빼지 않는다. 시작·종료 비용과 스케줄링 변동은 남는다. 구간에 0이 포함돼도 동등성 인증은 아니다.

별도 실행 폴더의 plan.json·samples.json·diagnostic.json을 확인한다. 중단·오류도 결과에 남긴다. 이 과정은 Unity·Bridge·네트워크 요청을 사용하지 않는다. 다른 벤치와 동시에 수행하지 않는다. 자동화에서는 `UnityBridgeDesk.Worker.exe --calibrate <출력 부모 폴더>`를 사용할 수 있다.

계측 진단도 일반 로컬 벤치와 같은 실행 잠금을 사용한다. 다른 Desk 로컬 벤치가 진행 중이면 시작을 막는다. 이 잠금으로 다른 프로그램의 CPU 사용까지 막지는 않는다.

**실행 중 진행 갱신 최소화**는 상세 로그 표시와 Unity·측정 단계 화면 갱신을 줄인다. 준비·시행 완료·정리·결과 기록은 유지한다. 계측기는 바꾸지 않는다. 이 옵션 자체가 UI 영향 제거의 증거는 아니다. 서로 다른 갱신 정책의 사전 계획을 갖는 실험을 별도 세션에서 비교해야 한다.

## 연구 자료 ZIP과 독립 검산

결과 → 내보내기 → **연구 자료 ZIP 저장…**을 사용한다. 기존 파일을 덮어쓰지 않는 새 이름을 선택한다.

| 파일 | 내용 |
|---|---|
| run.json | 모든 계획 시행과 기록된 성공·실패·미수행, 옵션·환경의 사본 |
| frozen-plan.json | 실행 전 계획 원문. 과거 기록에는 없음 |
| research-summary.txt | 계획 확인·A/A 진단·성공 및 제외 내역·해석 범위 |
| expected-analysis.json | 앱에서 계산한 시행 평균 구간·쌍 시간비 구간 |
| verify_analysis.py | 별도 Python 3.10+ 구현. 추가 패키지·Unity·인터넷 불필요 |
| SHA256SUMS.json | ZIP 안 파일의 손상 확인용 해시 |
| README.txt | 검산·재실행·공개 전 확인 방법과 한계 |

ZIP을 새 폴더에 풀고 `python verify_analysis.py`를 실행한다. 원시 기록에서 상위 시행을 다시 집계하고 쌍을 만든다. 반복 F01·F03·F04의 대표시간도 원시 호출 평균과 대조한다. Student 밀도의 수치 적분으로 분위수를 구하고, 쌍 차이의 t 구간을 수치 역산한다. 앱의 불완전 베타 함수·이차방정식 해 계산을 호출하지 않는다. 비교 허용 오차는 수치 검산용 상대 1e-6·절대 1e-7이며 A/A 허용 차이와 다르다. 실패 또는 파일·계획·계산 불일치는 종료 코드 1, 산술 검산 완료는 0이다. analysis-check.json에 재계산 결과를 쓴다.

이 검산은 전체 명령을 재실행하거나 통계적 독립성을 증명하지 않는다. 새 F02 관측 자료가 있으면 독립 정답 검사를 추가로 수행한다. F02는 명령 간 간격을 포함하는 실제 전체 구간이므로 개별 호출의 합으로 교체하지 않는다. S01의 동시 표본도 독립 시행으로 늘려 세지 않는다. 보고서 형식은 12이며 기존 형식 11 이하의 출력과 원본은 보존한다.

개인 경로·사용자 명령이 결과에 포함될 수 있다. 공개 전 확인한다. 자격 증명·개인 폴더·진단 로그 전체를 무차별 수집하지 않는다. 원시 로그·필요한 실제 결과 증거와 논문 전용 그림·표 재생성 스크립트는 연구 자료 범위에 맞춰 별도로 공개한다. 실행 바이너리 재배포는 각 라이선스를 확인한다.

## 남은 검증과 다음 단계

이번 구현 검사와 첫 합성 진단의 수치는 [2026-09-21 검증 기록](RESEARCH-CHECKS-20260921.md)에 정리한다. 정상 실행 완료와 계측 정확성 검증은 구분한다.

1. 실제 Unity에서 A/A를 수행하고 독립된 세션에 재실행한다. 현재 구현 검사 결과를 실제 A/A 결과라고 부르지 않는다.
2. 실제 호출 추세로 준비 정책·반복 수를 확정하고 별도 본시험을 한다. OS 캐시·온도·클럭·외부 부하의 영향을 평가한다.
3. 대표적인 실제 작업을 선정한 근거와 제품별 어댑터의 동등성을 확인한다. 현재 공통 작업 전체를 모든 내장 명령·AI 능력으로 확대하지 않는다.
4. 비대칭·꼬리가 긴 분포·의존성·선택적 실패에서 구간의 성질을 더 검증한다. 현재 Python 검산은 같은 자료의 산술 일치 확인이다.
5. 별도 팀이 같은 계획으로 실행하고 자료를 재분석한다. 장비·세션 결과를 무조건 한 평균으로 합치지 않는다.

참고: [Kalibera·Jones 정정 원고](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf), [NIST 실험 설계](https://www.itl.nist.gov/div898/handbook/pri/section3/pri33.htm), [ACM PADS 산출물 평가](https://sigsim.acm.org/conf/pads/2024/blog/artifact-evaluation/). 이 문서의 A/A 범위·수치 하한·진단 수준은 Desk의 설계 선택이다.

## UI 적용 근거

프로젝트 design/UI-DESIGN-WORKFLOW.md와 docs/UI-NAVIGATION.md를 읽었다. 2026-09-21 frontend-design/SKILL.md 및 UI/UX Pro Max/SKILL.md·quick-reference.md 원문을 참고했다. 외부 스킬을 설치하거나 검색 데이터베이스를 실행한 것은 아니다. 기존 Paper·Ink·AccentInk·Muted 색상 토큰과 WPF 글자 체계를 유지한다. 실제 색상은 선택한 기존 테마를 따른다.

frontend-design의 실제 내용에 맞는 문구와 장식 억제를 적용한다. UI/UX Pro Max의 점진적 공개, 명시적 입력 이름, 키보드 조작·좁은 화면의 줄바꿈을 적용한다. 웹 hero·CSS·GSAP와 새 팔레트 예제는 적용하지 않는다. 새 탭이나 카드 열을 추가하지 않고 준비의 접힌 연구 설정과 기존 내보내기 메뉴에 배치한다. 모션·캐릭터·배경 자산은 바꾸지 않는다. 실제 WPF 렌더링과 설정 왕복·시작 조건을 검사한다.
