# v0.2.0 F02 연결 검색 실패 확인

2026-09-17 저장 기록을 조사했다. F02의 같은 오브젝트 이동 작업을 100개 명령으로 나눠 보내는 조건에서 v0.2.0의 #36은 14개 성공 후 15번째, #39는 18개 성공 후 19번째 명령이 실패했다. 같은 실행의 v0.2.1·v0.2.3·v0.3.0-rc.1은 이 조건을 각각 두 번 모두 100개 완료했다. 이는 해당 실행의 관찰값이며 모든 환경의 실패 확률로 일반화하지 않는다.

CLI는 종료 코드 1과 표준 오류의 `{"ok":false,"error":"no active instance on port 8090"}`를 반환했다. #39의 Editor 로그에는 8090 포트 서버 시작 기록이 있다. 당시 연결 파일 접근 오류나 종료 직전 프로세스 상태는 수집하지 않았으므로 Unity 종료·파일 접근 충돌 중 어느 원인인지 기록만으로 확정할 수 없다.

v0.2.0의 CLI는 연결 파일을 읽을 때 OSError가 발생하면 해당 파일을 건너뛴다. v0.2.1은 Windows에서 연결 정보 파일 교체 중 PermissionError가 발생하는 경우 10ms 간격으로 최대 4번 더 읽는다. 다음은 비교한 공식 소스이다.

- [v0.2.0 client.py](https://github.com/zjxps2007/UnityBridge/blob/0313bb5804c5fd8bff1dfdad1a5e1c38d37f93d6/src/unity_bridge/client.py)
- [v0.2.1 client.py](https://github.com/zjxps2007/UnityBridge/blob/7fb26ae4fc856cf0e176efac23e94506e4749c91/src/unity_bridge/client.py)

캐시된 두 릴리스의 수정하지 않은 클라이언트 소스에 동일한 파일 읽기 충돌을 주입해 확인했다. 첫 읽기는 PermissionError, 다음 읽기는 정상 연결 정보를 반환하도록 한 합성 검사에서 v0.2.0은 한 번 읽고 같은 오류를 반환했다. v0.2.1은 10ms 대기 후 두 번째 읽기에서 연결을 찾았다. 이 검사는 가능한 실패 메커니즘을 재현한다. 실제 #39에서 그 충돌이 발생했다는 직접 증거는 아니다. 실제 Unity 벤치를 이번 수정의 검증으로 다시 실행하지 않았다.

Desk는 빈 표준 출력만 JSON으로 읽던 오류 처리를 수정한다. 앞으로 CLI의 구조화된 표준 오류를 우선 해석하고 연결 검색 실패를 별도로 표시한다. 이전 결과도 해당 오류 원문이 있으면 읽기 쉽게 표시하며, 시행 상세에 ‘계획 100개 중 19개 호출 · 응답 검증 통과 18개 · 실패 1개 · 첫 실패 19번째’와 같이 진행 지점을 제공한다. 보고서 형식 변경 시 기존 파일을 덮어쓰지 않고 새 사본을 만든다.

비교 대상 CLI·Connector를 패치하거나 실패 명령을 자동 재실행하지 않는다. 그렇게 하면 배포된 원래 버전의 안정성과 속도를 측정한다는 조건이 달라진다. 실패 시행은 속도 평균에서 제외하고 안정성의 실패 수와 부분 호출 기록에 남긴다. 성공한 18개만으로 100개 전체 작업 시간을 대체하지 않는다.
