# 연구 검증 보완: 사용법과 측정 범위

2026-09-21. v0.5.0 미배포 변경이다. 구현 검사, 합성 실험, 실제 Unity 실험, 외부 재현은 서로 다른 증거이다.

## 앱에서 사용하는 순서

준비 화면의 **실험 목적**에서 선택한다. 본시험·검증을 고르면 **연구 계획·세션 기록**을 펼친다.

| 목적 | 필요한 설정 | 결과에서 확인할 것 |
|---|---|---|
| 버전 속도 비교·탐색 | 2~8개 대상 | 시간과 전체 계획 중 유효·실패 수 |
| 반복 수를 정할 예비 실험 | 2~8개 대상, 예비 반복 설계 | 분산·순서 진단, 다음 반복 수 제안 |
| 계획을 고정한 본시험 | 연구 질문·주 비교·반복 수의 이유 | 고정 계획 일치와 개별 비교의 불확실성 |
| 같은 릴리스 검증·A/A | Bridge 1개, 질문·허용 차이의 이유 | 같은 파일 A/B의 시간비 95% 구간 |
| 알려진 지연 감지·+100ms | Bridge 1개, F01만, 연구 질문 | 외부 증가와 실제 Unity 내부 증가 |

본시험·검증은 새 프로젝트 5회 이상이고 대상 수의 배수여야 한다. A/B라면 짝수이다. 최소 입력 조건이며 충분성 보장이 아니다. 연구 묶음·세션 메모는 선택 입력이다. ID는 실행마다 생성하며 실행 기록에서 묶음 이름과 ID로 검색한다.

잘못 입력하면 오류를 글로 표시한다. **확인할 항목으로** 동작으로 해당 입력을 펼쳐 이동한다. A/A 허용 차이는 A/A에서만 입력한다. 총 시행 수를 확인한 뒤 벤치를 시작한다. 목적 변경이 실험 선택·반복 수를 몰래 바꾸거나 자동 실행하지 않는다.

결과의 **시행 포함 범위·연구 기록**에서 계획·세션·파일 명세와 대상별 유효·실패/제외·중단·미수행을 읽는다. **같은 조건으로 새 세션 준비**는 조건·묶음을 복원하고 세션 메모만 비운다. 과거 자료와 자동 합산하지 않는다. **자료 내보내기 → 연구 자료 ZIP 저장**에서 원시 자료와 검산기를 받는다.

## A/A와 지연 감지

A/A는 동일 CLI·Connector를 A/B로 나눠 독립된 프로젝트·프로세스에서 실행한다. 95% 시간비 구간 전체가 사전 허용 범위 안인지 확인한다. 20쌍 하한과 기본 1%는 인증된 충분성 기준이 아니다. 0% 차이를 포함한다고 동등하다고 말하지 않는다. 이 구간 포함 규칙은 일반적인 유의수준 5% TOST 구현과 구분한다. [Lakens, 2017](https://pure.tue.nl/ws/portalfiles/portal/80918653/lakeequi2017.pdf)

지연 감지는 B의 F01 echo 본문에만 100ms 대기를 넣는다. A는 대기하지 않는다. 반복 조건의 사전 실행에도 각 대상의 같은 요청을 쓴다. Unity 메인 스레드에서 Stopwatch로 실제 대기 구간을 기록하며 `Thread.Sleep(100)`이 정확히 100ms라고 가정하지 않는다. 이 의도적 부하는 진단 전용이다.

기존 외부 측정 경계는 CLI 프로세스 시작부터 종료·출력 수집까지이다. 유효 쌍별 외부 차이 평균과 t 기반 95% 구간, 실제 내부 차이 평균, `외부 증가−내부 증가` 잔차를 보고한다. 서로 다른 시계의 절대 시각을 빼지 않고 각자 측정한 기간을 비교한다. 내부 기간은 `InnerDelayMs`와 CSV 마지막 열에 남는다. 잔차는 고정 보정값이나 정확성 인증이 아니다. [Microsoft 경과 시간 계측](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)

A/A로 놓칠 수 있는 공통 편향을 지연 대조로 함께 조사할 수 있지만 실제 Unity 자료가 있어야 평가할 수 있다. 구간에는 시행 간 독립성 등의 가정도 남는다.

## 순서·세션·파일 동일성

반복 회차마다 모든 조건의 순서를 섞는다. 각 조건에서는 모든 버전이 들어가는 블록을 만들고, 무작위 대상 배열을 순환 이동하는 주기를 사용한다. 반복 수가 대상 수의 배수이면 대상별 각 실행 위치의 횟수가 같다. 같은 시드는 배치를 재현하지만 시행 ID는 새로 생성한다. 표시 순서는 측정 순서와 분리해 조건·버전별로 고정한다.

[NIST 무작위 블록 원칙](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)을 참고한 설계이다. 모든 직전 대상 조합·조건 위치의 횟수가 같은 것은 아니다. 조건 간 잔여 영향·장기 추세·세션 상관은 별도로 확인한다.

계획에는 실행 ID, 시각, 연구 묶음·메모, OS·런타임·CPU·전원, 가동 시간과 추정 부팅 시각을 기록한다. 각 시행 직전 메모리·전원 기록도 유지한다. 추정 부팅 시각은 인증된 부팅 ID가 아니다. 여러 실행이 곧 독립 표본이라는 뜻도 아니다.

시작 전에 Desk·Worker 실행 파일·관리 DLL·런타임·deps/runtimeconfig·Assets의 상대 경로·크기·SHA-256을 기록한다. 사용자 설정·인증·로그는 수집하지 않는다. 기존 CLI·Connector·의존 패키지 검사와 결합한다. 측정 밖의 파일 읽기가 OS 캐시에 주는 영향은 남는다.

이 명세는 시작 시점 배포 파일의 기록이다. Unity 설치 전체, 실행 도중 일시적 변조, 소스 커밋과 빌드의 대응을 인증하지 않는다. 소스 커밋·실제 배포 ZIP 해시와 전체 Unity 환경 고정, 외부 재현이 추가로 필요하다.

## 정답과 증거

F02는 측정 후 Unity의 실제 객체 이름·좌표를 읽고 Worker가 별도로 기대 ID·개수·위치를 계산한다. 객체 나열 순서는 무관하며 ID 중복·개수 차이·유클리드 위치 오차 0.00001 이상이면 실패이다. 조회·파일 기록·정답 검사는 측정 밖이다. [도구별 대응과 대표성](WORKLOAD-EQUIVALENCE.md)

`scene-observed.json`의 SHA-256을 시행 결과와 연결한다. 연구 ZIP은 일치하는 파일만 포함하고, 없는 자료는 누락으로 표시한다. 독립 Python 검산기도 성공한 F02 관측을 다시 검사한다. 실패 관측은 실패 증거로 보존한다. Unity 관측 코드 자체의 버그나 허위 응답까지 배제하는 보안 인증은 아니다.

ZIP은 원시 기록·고정 계획·연구 요약·전체 계획 분모·실행기 명세·F02 관측/누락 안내·기대 분석·독립 Python 검산기·해시 목록을 담는다. 새 폴더에 풀고 `python verify_analysis.py`를 실행한다. Python 3.10 이상 표준 라이브러리만 필요하며 결과는 `analysis-check.json`이다. 로컬 경로·명령·사용자 입력은 공개 전에 검토한다.

규칙은 `desk-research-v2`, 순서는 `randomized-condition-rounds-latin-target-cycles-v2`, 보고서 형식은 12이다. 이전 v1 계획과 없는 기록을 읽고 원시 결과·이전 내보내기를 덮어쓰지 않는다. 로컬 해시는 외부 사전등록이 아니다. [OSF](https://help.osf.io/article/330-welcome-to-registrations)와 [Zenodo](https://zenodo.org/help/versioning) 공개 절차는 별도로 진행해야 한다.

## 실패·부하·통계의 한계

성공 평균 옆에서 계획 전체의 유효·실패/제외·중단·미수행을 확인한다. 준비 오류·정리 실패도 숨기지 않는다. 이는 기존 S01의 평가 가능한 시행 분모와 구분된다. 같은 부하 시행의 요청을 독립 표본으로 세어 성공률 구간을 붙이지 않는다. 시간 초과는 실제 완료 시간도 0ms도 아니다.

S01은 완료 뒤 다음 요청을 보내는 **고정 동시성** 시험이다. 일정 도착률의 대기 시간 실험은 아직 아니다. [wrk2 요청 공급 모델 설명](https://github.com/giltene/wrk2#readme)을 참고해 차이를 명시했다. 도착률 모드에는 별도 연구 질문, 예정·제출·완료 시각, 대기열·누락·발생기 병목·상한 정책이 필요하다. 기존 지연값에 소급 보정을 하지 않는다.

여러 비교는 개별 95% 구간이다. Holm 보정이나 동시 우열 보장을 적용했다고 표시하지 않는다. 본시험 질문에 주 비교와 분석 범위를 먼저 적고, 다중 검정·동시 구간은 별도 검증이 필요하다.

**Unity 없이 실행기 진단**은 자식 프로세스 60회 시험이며 화면과 `00_진단요약.txt`로 읽는다. 실제 Unity 진단과 다르고 벤치와 실행 잠금을 공유한다. 통계 모의실험은 앱이 실행하지 않는 별도 도구로 둔다. [수식 민감도 도구와 기록](RESEARCH-SIMULATION.md)

실제 Unity A/A·지연 감지, 여러 세션·PC의 재현, 예비 분포 기반 표본 수·워밍업, 작업 대표성, 상관·다중 비교를 반영한 분석, 제삼자 재실행이 남는다. 고정 횟수 준비 호출만으로 정상 상태를 가정하지 않는다. [Barrett 등의 워밍업 연구](https://theunixzoo.co.uk/pubs/pdf/barrett2017warmup.pdf)는 점검 근거이며 Unity 자체를 검증한 논문은 아니다.

디자인 근거는 [UI·UX 적용 기록](RESEARCH-UX-20260921.md), 검사 결과는 [보완 검증 기록](RESEARCH-EXTENSION-CHECKS-20260921.md)에 구분한다.
