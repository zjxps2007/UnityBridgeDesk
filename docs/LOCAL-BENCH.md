# 로컬 속도 벤치의 근거와 검증 범위

v0.3.1 정식 앱의 측정 구현과 검증 범위입니다. 별도 가상머신을 준비하지 않고, 설치·활성화된 Unity로 같은 PC 안에서 버전별 속도를 비교합니다. 사용자는 Unity 선택을 확인하고 릴리스를 골라 벤치를 시작합니다. 파일·프로세스의 분리는 앱이 수행합니다. 기본 설정·분석이 예비 수준이라는 의미의 pilot 스키마는 앱 배포 단계와 구분합니다.

## 해결하는 부분과 남는 부분

| 관심 사항 | 현재 처리 | 남는 한계 |
|---|---|---|
| PC 자원 사용 | 해당 PC에서 실행하고 버전을 순차 측정. 종료·취소 시 시험 프로세스 묶음을 종료 | 측정 중 CPU·메모리·디스크를 사용하며 다른 앱과 경쟁 |
| 환경 차이 | 한 실행에서 같은 Unity·Windows 사용. 파일 해시·버전·메모리 상태 기록 | 다른 PC 간 결과가 같아지지는 않음. 사용자 설정·레지스트리·서비스 공유 |
| 이전 실험 파일 | 매 시행 새 프로젝트·Library·CLI 복사본·TEMP/TMP·UPM 캐시 사용 | Windows 파일 캐시, 외부 서비스의 캐시·로그는 공유 |
| dump·잔여 파일 | 시험 폴더 안의 dump 이름·크기 기록 후 폴더 삭제. 살아 있는 프로세스·소유 확인 | 전역 WER·라이선스 로그를 지우지 않음. 전원 차단 등 모든 잔여를 막지는 못함 |
| 설치 번거로움 | Unity 자동 탐색, 릴리스 자동 준비, 정상 종료 후 자동 정리 | Unity의 최초 설치·활성화와 최초 릴리스 다운로드는 필요 |

이 기능은 파일과 프로세스를 분리하는 실행 방식입니다. 새 Windows 사용자, 컨테이너, 보안 샌드박스나 OS 초기화 기능을 제공한다고 해석하면 안 됩니다. 특히 TEMP/TMP만 바꾸어 사용자 프로필과 AppData가 격리되었다고 주장하지 않습니다.

## 실행과 정리

1. 공식 릴리스 태그를 커밋에 고정하고 CLI·Connector와 RC 런타임 전체의 해시를 확인합니다.
2. `speed/local-work/<시행 ID>` 아래에 소유 표식과 새 프로젝트·배포 파일을 만듭니다. 기존 프로젝트를 사용하지 않습니다.
3. Worker와 그 자식 Unity·CLI에 해당 시행의 TEMP/TMP·UPM 캐시 경로를 전달합니다. Unity crash 경로도 시행 폴더로 지정합니다.
4. Worker는 시작 허가를 받기 전에 Windows Job Object에 연결됩니다. Unity 준비·컴파일·Bridge ready 이후 고정 명령을 측정합니다.
5. 응답 값, 요청 식별자, 프로젝트·프로세스 ID를 검증하고 결과와 제한된 크기의 로그를 저장합니다.
6. 프로세스 묶음의 종료를 기다린 뒤 관리 경로·소유 토큰·실행 상태·연결 폴더 여부를 확인해 삭제합니다. 종료나 정리 확인이 실패하면 다음 시행을 진행하지 않습니다.

기존 개인 Unity를 이름으로 찾아 종료하지 않습니다. 공유 Bridge 인스턴스 목록에서는 해당 시험의 프로젝트 경로와 기록된 PID가 모두 일치하는 항목만 정리합니다. 다음 벤치 시작 전에도 이전 작업 폴더의 소유권과 실행 상태를 확인합니다. 같은 사용자 환경에서는 동시 벤치를 막는 파일 잠금을 사용합니다.

## v0.3.1의 중단 후 정리 복구

읽기 전용 UPM 임시 파일의 속성은 소유권과 프로세스 종료를 확인한 관리 폴더 안에서만 해제합니다. 내용부터 삭제하고 `.local-owner.json`은 마지막에 제거합니다. 폴더 밖의 `<시행 ID>.cleanup.json`에도 정리 소유 정보를 보존해 마지막 삭제 단계에서 강제 종료돼도 재시도할 수 있습니다.

v0.3.0에서 표식이 이미 사라진 폴더는 `local-runs`의 요청·시행 ID·작업 경로·정리 실패 기록을 대조하고 기록된 Worker·Unity가 종료된 경우에만 복구합니다. 이름이 GUID라는 이유만으로 삭제하지 않으며, 근거가 부족하면 폴더를 보존하고 안내합니다. 결과 JSON·CSV·설정·받아둔 릴리스는 유지합니다.

## 이렇게 측정하는 이유

**환경을 완전히 없앨 수는 없으므로 비교 조건을 맞추고 변동을 드러냅니다.** 매 시행 새 프로젝트와 프로세스를 만드는 이유는 앞선 버전이 생성한 오브젝트·파일·프로세스 메모리가 다음 시행에 직접 넘어가는 것을 줄이기 위해서입니다. Windows는 파일 데이터를 시스템 캐시에 보관하므로 새 폴더나 새 프로세스가 곧 차가운 디스크 캐시를 뜻하지는 않습니다. [Microsoft 파일 캐시 문서](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching)

**중단 뒤에도 시험 프로세스가 남지 않도록 수명 관리를 묶습니다.** Job Object는 관련 프로세스를 한 단위로 관리하고 마지막 핸들이 닫힐 때 종료하도록 설정할 수 있습니다. 이것만으로 파일 접근·네트워크·사용자 설정까지 격리되는 것은 아닙니다. [Microsoft Job Object 문서](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

**캐시 경로는 Unity가 지원하는 설정을 사용합니다.** 자식 프로세스의 UPM 캐시 환경 변수로 패키지 캐시를 시행별로 지정하고, crash 경로도 Unity 실행 옵션으로 지정합니다. 이 범위를 벗어난 공용 로그·라이선스 데이터까지 자동으로 초기화하지 않습니다. [Unity UPM 캐시 설정](https://docs.unity3d.com/cn/6000.0/Manual/upm-config-cache.html), [Unity 로그·crash 경로](https://docs.unity3d.com/cn/2023.2/Manual/LogFiles.html)

**버전의 순서와 실패도 결과에 포함합니다.** 조건별 블록 안에서 버전 순서를 회전하고 시드로 반복 순서를 정해 한 버전이 계속 먼저 실행되는 편향을 줄입니다. 블록화와 무작위화는 시간에 따른 외부 조건 변화의 영향을 줄이기 위한 실험 설계 원칙입니다. 현재의 제한된 순서 회전은 모든 조건을 완전 무작위화한 설계와 같지 않습니다. 실패는 0ms로 취급하지 않고 같은 블록의 두 버전 모두 성공한 경우만 시간 비교에 사용합니다. [NIST 실험 설계](https://www.itl.nist.gov/div898/handbook/pri/section3/pri33.htm)

**시간의 경계를 고정합니다.** CLI 시작 직전부터 종료와 출력 수집까지 재고, 다운로드·Unity 준비·해시 검사·검증·정리는 별도로 둡니다. 첫 호출의 정의와 F01·F02·F03 명세는 [BENCHMARKS.md](BENCHMARKS.md)에 있습니다. 결과는 `local-cli-completion-v1-pilot`로 기록해 이전 VM 결과와 섞지 않습니다.

## 2026-09-15 실제 확인

v0.3.1(2026-09-16)에서는 읽기 전용 파일, 삭제 중 파일 잠금, 소유 표식 유실, 살아 있는 프로세스, 잘못된 경로·소유 기록, 정리 기록 복구를 검증하는 회귀 검사 8개를 추가했습니다. 전체 178개 검사가 통과했고, 실제 발생한 잔여 폴더 1개를 복구한 뒤 기존 설정·릴리스·결과 351개 파일의 해시가 유지됨을 확인했습니다. 이번 수정에서는 Unity 성능 시험을 다시 수행하지 않았습니다. 아래는 v0.3.0에서 확인한 통합 실행 기록입니다.

일반 자동 검사는 Unity를 실행하지 않는 170개 검사로 파일 소유권·범위 밖 삭제 거부, 손자 프로세스 종료, 응답 검증, RC 설치와 WPF 화면·설정 동작을 확인했습니다.

별도로 이미 활성화된 Unity **6000.3.23f1**, Windows 11, Ryzen 7 5700X·32GB PC에서 다음 실험을 수행했습니다.

| 실제 통합 확인 | 대상 | 결과 |
|---|---|---|
| F01 first / prepared | 0.2.0·0.2.1·0.2.2-rc.2 | 6개 시행 모두 응답 검증 성공·폴더 정리 확인 |
| F02 1/10/100개 명령 | 0.2.1·0.2.2-rc.2 | 6개 시행 모두 성공·정리 확인 |
| F03 1 KiB/64 KiB/1 MiB | 0.2.1·0.2.2-rc.2 | 6개 시행 모두 성공·정리 확인 |
| Unity 실행 단계에서 중단 | 0.2.1, 다음 버전 미실행 | 중단 기록·프로세스 종료·폴더 정리 확인 |

통합 확인은 조건당 1개 새 프로젝트와 최소 호출로 기능을 점검한 것입니다. 이 18개 성공만으로 버전 간 통계적 우열이나 다른 PC·Unity 버전의 호환성을 확정하지 않습니다. 최초 제한된 개발 실행에서는 Unity 라이선스 데이터 접근이 개발 도구의 실행 제한에 막혀 실패했고, 권한이 허용된 실제 PC 실행으로 분리해 확인했습니다. 그때 남은 소유 폴더도 다음 실행에서 정리됐습니다.

남은 범위는 여러 PC·Unity 버전의 확인, CPU 부하·온도·전원 상태 자동 통제, OS 공용 캐시 초기화와 실제 환경에서의 통계 가정 검토입니다. 평균·쌍 시간비 신뢰구간과 예비 반복 설계는 [논문 방법론 적용](STATISTICAL-METHODOLOGY.md)에 따라 추가했습니다. 사용자 프로필이나 공용 캐시를 임의로 지워 환경 한계를 감추지 않습니다.
